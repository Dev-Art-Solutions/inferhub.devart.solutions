InferHub

A self-hosted, Ollama-compatible inference mesh. Run the gateway where you have no GPU. Run worker nodes where you do.

InferHub puts a small, always-on coordinator in front of a pool of nodes that live on your GPU machines. The coordinator speaks an Ollama-shaped HTTP API; the nodes reach out to the coordinator over SignalR and pull jobs down — so they work fine behind NAT, with no port forwarding and nothing exposed to the public internet.

   

The node backend is powered by OllamaClient — our open-source .NET library for Ollama. The full library documentation, configuration, and API reference live at ollamaclient.devart.solutions.

The problem

GPUs and servers rarely live in the same place. The machine that is always on — a small VPS, a home server — usually has no GPU. The machines that do have a GPU — a desktop, a gaming rig, a workstation — are often behind a home router and not reachable from outside.

InferHub closes that gap. A lightweight coordinator runs on the always-on, GPU-less host and speaks a familiar Ollama-style API. The actual work runs on nodes that sit on your GPU machines, reach out to the coordinator, and pull jobs down.

In short: one stable address in front, a pool of GPUs behind it.

How it works

                                  ┌──────────────────────────────┐
   client (Ollama-compatible)     │          Coordinator         │
   curl / app / IDE plugin  ─────▶│  Ollama-style HTTP API       │
        (Bearer token if remote)  │  /api/tags /api/generate     │
                                  │  /api/chat                   │
                                  │                              │
                                  │  SignalR node hub  ◀─────────┼──── persistent outbound
                                  └───────────────┬──────────────┘     connection from nodes
                                                  │
                         dispatch (model-aware)   │   stream tokens back
                          ┌───────────────────────┼───────────────────────┐
                          ▼                       ▼                       ▼
                   ┌────────────┐          ┌────────────┐          ┌────────────┐
                   │   Node A   │          │   Node B   │          │   Node C   │
                   │  + Ollama  │          │  + Ollama  │          │  + Ollama  │
                   │  (GPU)     │          │  (GPU)     │          │  (GPU)     │
                   └────────────┘          └────────────┘          └────────────┘
  • Coordinator — an ASP.NET Core service. It exposes an Ollama-compatible HTTP API, authenticates remote callers with a Bearer token, keeps track of which nodes are online and which models each one holds, and routes every request to a capable node.
  • Node — a small .NET worker. It opens a persistent outbound connection to the coordinator (so it works fine behind NAT), reports which models it can serve, then receives prompts, runs them against its local inference backend, and streams the result back.
  • Pluggable backends — each node runs an LLM backend behind a small abstraction (IInferenceBackend). The first backend is Ollama, driven by our own OllamaClient library. Other backends (vLLM, llama.cpp, OpenAI-compatible servers) can slot in later without touching the coordinator.

Because the API is Ollama-shaped, existing Ollama clients, scripts, and editor plugins can point at the coordinator and keep working — they just reach a whole pool of GPUs instead of one.

Quick Start

One command with Docker, or two processes from source.

Docker

Fill in three keys, then bring the stack up:

cp deploy/docker/.env.example deploy/docker/.env   # set the three keys
docker compose -f deploy/docker/docker-compose.yml up -d

Images are published to GHCR for linux/amd64 and linux/arm64. See Docker for the full picture — including why the keys are mandatory there and optional below.

From source

On the always-on host (no GPU needed) start the coordinator:

dotnet run --project src/InferHub.Coordinator

On each GPU machine (with Ollama already running locally on :11434) start a node:

dotnet run --project src/InferHub.Node

From anywhere, talk to the coordinator like it is Ollama. Remote calls need a Bearer token:

curl http://your-coordinator:5080/api/chat \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -d '{"model":"llama3","messages":[{"role":"user","content":"Hello!"}],"stream":false}'

That's it. The coordinator picks a node that holds llama3, runs the request there, and streams the response back. Prefer an OpenAI SDK? Point it at /v1 instead — see below.

Just a node (v3.5+)

Both of the above run two processes so that one client can reach one backend. On a single machine that is all ceremony and no routing, so since v3.5 the node serves the same API itself — no coordinator, no enrollment secret, no internet.

dotnet run --project src/InferHub.Node \
  --LocalApi:Enabled=true --Coordinator:Enabled=false

Then change one string and nothing else:

# before — the fleet
client = OpenAI(base_url="http://hub.example:5080/v1", api_key=KEY)
# after — just the node
client = OpenAI(base_url="http://localhost:5081/v1", api_key=KEY)

See Solo mode for the full surface and the three things it deliberately refuses.

One container, with or without a GPU (v3.7+)

The same thing again with nothing installed on the host — the bundled image carries Ollama inside it, and uses your card if you pass one in:

docker run -d --name inferhub --gpus all \
  -e LocalApi__Enabled=true -e Coordinator__Enabled=false \
  -e LocalApi__ApiKeys__0="$INFERHUB_API_KEY" \
  -v inferhub:/data -p 5081:8080 \
  ghcr.io/dev-art-solutions/inferhub-node:ollama

docker exec inferhub ollama pull llama3.2

Drop --gpus all and it runs on the CPU instead. See One container, with or without a GPU.

…and it can transcribe (v3.10+)

The same line against the :tools tag brings Whisper and Piper with it:

docker run -d --name inferhub --gpus all \
  -e LocalApi__Enabled=true -e Coordinator__Enabled=false \
  -e LocalApi__ApiKeys__0="$INFERHUB_API_KEY" \
  -v inferhub:/data -p 5081:8080 \
  ghcr.io/dev-art-solutions/inferhub-node:tools

curl http://localhost:5081/v1/audio/transcriptions \
  -H "Authorization: Bearer $INFERHUB_API_KEY" \
  -F file=@meeting.m4a -F model=whisper-small

Without --gpus all it transcribes on the CPU, and says so in its first log line. See Speech in, speech out.

One box that makes pictures (v3.14+)

docker run -d --gpus all \
  -e LocalApi__Enabled=true -e Coordinator__Enabled=false \
  -e LocalApi__ApiKeys__0="$INFERHUB_API_KEY" \
  -v inferhub-images:/data -p 5083:8080 \
  ghcr.io/dev-art-solutions/inferhub-node:diffusion

curl http://localhost:5083/v1/images/generations \
  -H "Authorization: Bearer $INFERHUB_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"sdxl","prompt":"a lighthouse in a storm, oil painting","size":"1024x1024"}' \
  | jq -r '.data[0].b64_json' | base64 -d > out.png

The weights are fetched in the background on first run, so sd15 is serving about a minute in and sdxl at three and a half — the model appears when it is ready, and no request waits on a download. This one needs a card. See Text to image.

Which image do I pull? (v3.14+)

There are five now, and five artifacts with no chooser is how somebody pulls 12 GB to run a 340 MB workload — or pulls the small one and wonders where the audio went. All tags live under ghcr.io/dev-art-solutions/.

Pull thisSizeArchWhen it is the right one
inferhub-coordinator~120 MBamd64 + arm64The always-on host. No GPU and no inference engine — it routes, serves the client API and hosts the console.
inferhub-node~340 MBamd64 + arm64You already run Ollama, vLLM, LM Studio or a hosted OpenAI-compatible endpoint. Also the right one for solo mode and for a vector-store-only box.
inferhub-node:ollama~4 GBamd64One docker run on a GPU box with nothing installed on the host: Ollama runs inside the container, supervised by the node. :gpu is an alias of the same digest and works fine with no card.
inferhub-node:tools~6 GBamd64The above plus speech — Python, faster-whisper and piper, so /v1/audio/* works out of the box.
inferhub-node:diffusion~12 GBamd64Text to image — PyTorch, diffusers, bitsandbytes and seven recipes (SDXL, SD 1.5, FLUX.1-schnell, Qwen-Image, SD 3.5 Medium, SDXL-Turbo and qwen-360), so /v1/images/generations works out of the box. You need a card.

Three rules of thumb that save the mistake each way. Do not pull :tools for chat — it is :ollama plus ~1.5 GB of Python wheels nothing will load, and every image above it does chat identically. Do not pull :ollama to point at an Ollama you already run — the bundled one idles beside it, or fights it for the port, and the loser is whichever one's logs you are reading. :diffusion is the one image that does not stack, and that is deliberate: it has no Ollama, no Whisper and no Piper in it, because a card running a diffusion pipeline has no room for a chat model beside it. Want both? Run two containers and let the coordinator route image to one and chat to the other — that is what capability routing is for.

Whichever node image you choose, mount a volume at /data: model weights, the node's stable id, tool scratch and any corpus live there, and without it every docker run re-downloads gigabytes.

Solo mode — just the node (v3.5+)

A coordinator, a node, an enrollment secret and two processes — to route between one client and one backend. For a single machine that is all cost and no benefit.

InferHub had exactly one shape until v3.5: a coordinator somewhere always-on, and nodes on GPU machines dialling out to it. That shape is right when you have a fleet and it is overhead when you have one machine — and one machine is how most people start, and how a lot of people stay.

// src/InferHub.Node/appsettings.json
{
  "Coordinator": { "Enabled": false },
  "LocalApi": {
    "Enabled": true,
    "Urls": "http://localhost:5081"
  }
}

Same request bodies, same responses, same streaming, same error envelope — both the OpenAI dialect at /v1 and the Ollama one at /api, including tool calls and vision. A solo node is the hub's formatting layer sitting directly on the node's executor, with the routing layer removed: the hub translates a request, routes it, queues it, dispatches it over SignalR and formats what comes back; solo does the first and the last and skips the middle, because there is nothing to route to. Both ends were already shared code, which is why none of it had to be reimplemented.

What it serves

RouteSoloNotes

POST /api/embed, /api/embeddings✅
GET /api/tags, /api/version✅/api/tags honours Node:Models:Include/Exclude — the same filter the node reports to a hub.
POST /v1/chat/completions, /v1/completions✅Blocking and streaming (SSE).

Retrieval on a standalone node (v3.6+)

A machine with a folder of documents and one GPU is the deployment that most wants RAG. Since v3.6 a standalone node ingests, indexes and grounds its own answers — the same headers, the same augmented prompt and the same X-InferHub-Sources citations a coordinator produces, because it is the same code rather than a second copy of it.

"Coordinator": { "Enabled": false },
"LocalApi": {
  "Enabled": true,
  "Retrieval": { "Enabled": true, "DefaultEmbeddingModel": "nomic-embed-text" }
}
# ingest
curl localhost:5081/api/collections/handbook/documents \
  -H 'content-type: application/json' \
  -d '{"id":"leave-policy","text":"Employees accrue 25 days of annual leave each year."}'

# see what retrieves, before you trust it
curl localhost:5081/api/collections/handbook/search \
  -H 'content-type: application/json' -d '{"query":"how much annual leave?"}'

# ground an answer
curl localhost:5081/api/chat -H 'X-InferHub-Retrieve: handbook' \
  -H 'content-type: application/json' \
  -d '{"model":"llama3","messages":[{"role":"user","content":"how much annual leave?"}],"stream":false}'

That adds /api/collections/{c}/documents (ingest, list, chunks, delete), the /api/collections/{c}/search playground, the /api/vector/{c} data plane, and X-InferHub-Retrieve on both dialects. Vector, keyword and hybrid modes all work, as does the optional LLM reranker.

It requires Coordinator:Enabled=false, and says so by refusing to start otherwise. A node in a mesh already holds vector replicas derived from its coordinator; giving that same process an authoritative corpus of its own would put two sources of truth under one collection name — a locally ingested document invisible to the fleet, and a hub that will happily overwrite it. There is no safe configuration of that, so it is not offered. It refuses rather than quietly switching the feature off, because what gets switched off is grounding.

No PDF, and no external vector databases. The PDF text extractor ships with the coordinator only, so a PDF upload to a node gets a clean 415 telling you to convert the file or use a hub — never a silently bad extraction that fills a corpus with plausible nonsense. The local store is the only provider on a node. The corpus lives in LocalApi:Retrieval:DataDirectory (in Docker, /data/retrieval — mount a volume or it is ephemeral).

Two more things it deliberately will not do

No admin API and no console. There is one node and you are sitting at it. Model management stays hub-driven; in solo mode it is ollama pull in the terminal you already have open.

It is not a second kind of coordinator. A solo node serves its own clients and nothing else. Nothing about the fleet changes — the coordinator gained no code, meshed nodes behave exactly as before, and the outbound-only rule that lets a GPU box sit behind NAT with no inbound rule is untouched. Solo mode adds a surface for your own clients, which is why it needs no hub at all.

Auth, and the one place it refuses to boot

Off by default, and loopback when on. Loopback callers need no key (matching the hub's Auth:RequireAuthForLoopback), so local curl just works.

A non-loopback address with no keys fails startup, naming the key. That is stricter than InferHub usually is about somebody else's network, and the asymmetry is intentional: an unauthenticated inference endpoint hands arbitrary compute on your GPU to anyone who can reach the port, and the first sign of it is a bill or a melted card. LocalApi:AllowAnonymous=true is the explicit override for a trusted network, and it warns on every boot.

This bites in a container by design — the image binds a wildcard, so a containerised solo node needs a key:

docker run -e LocalApi__Enabled=true -e Coordinator__Enabled=false \
           -e LocalApi__ApiKeys__0=your-key \
           -e Ollama__Endpoint=http://host.docker.internal:11434/ \
           -p 5081:8080 ghcr.io/dev-art-solutions/inferhub-node:latest

Concurrency

Node:MaxConcurrency has always been advisory — a number the coordinator's router respects. In solo mode nobody is respecting it, so it is enforced locally: over the cap a request waits up to LocalApi:MaxWaitSeconds and then gets 503 + Retry-After, the same status and header as the hub's queue, so existing client retry logic behaves identically. Unset means unbounded, exactly as it does today.

Both at once

Coordinator:Enabled and LocalApi:Enabled are independent. A fleet node with the local API on is legitimate — useful for curling a node directly while debugging. Both off is a startup failure naming both keys: a node that neither joins a mesh nor serves anyone is a typo. The full key list is in Node configuration.

Since v3.7 none of this needs an Ollama on the host either — see One container, with or without a GPU.

One container, with or without a GPU (v3.7+)

Solo mode removed the coordinator. This removes the host install: a second image that carries its own Ollama, uses your card when you pass one in, and your CPU when you do not.

docker run -d --name inferhub --gpus all \
  -e LocalApi__Enabled=true -e Coordinator__Enabled=false \
  -e LocalApi__ApiKeys__0="$INFERHUB_API_KEY" \
  -v inferhub:/data -p 5081:8080 \
  ghcr.io/dev-art-solutions/inferhub-node:ollama

docker exec inferhub ollama pull llama3.2

Then point any OpenAI client at http://localhost:5081/v1. The node image never needed a GPU before, because the node never did the computing — it shelled out to an Ollama you installed, reached through host.docker.internal or 172.17.0.1, and kept alive yourself. Now there is something in the container that uses the card.

Three modes, one image

None of them refuses to start, and the node says in its first log lines which one it is in.

ModeHowWhat runs
GPU inference (+ RAG)--gpus allnode + Ollama on CUDA
CPU inference (+ RAG)leave --gpus offnode + Ollama on the CPU — right for embedding models and small ones
Vector store only-e Ollama__Supervisor__Enabled=falsenode + corpus, no Ollama process at all

The third is worth explaining: /api/vector/{collection} takes client-supplied vectors, so a node with no inference process is still a complete vector store. It reports zero models, which is the honest answer — a chat request fails cleanly instead of hanging. Ingesting documents does need an embedder, so there, either bring your own vectors or point Backend:Type=openai at an embedding upstream elsewhere. And it is still the 4 GB image: if that is all you want, the plain inferhub-node image does solo retrieval identically at 340 MB.

Did it get the card?

The node answers that in its first log lines, both ways:

info: CUDA: 1 device(s) visible to this process — NVIDIA GeForce RTX 3090 Ti.
info: CUDA: no devices visible to this process; inference will run on the CPU.
      In a container, pass '--gpus all' to use a card.

and on /api/status as a gpu block. For which device a loaded model actually ended up on, docker exec inferhub ollama ps is the ground truth — that is Ollama's own accounting, and it is not something InferHub second-guesses.

An earlier draft of this release refused to start without a GPU, and that was reversed. CPU is a legitimate mode, not a misconfiguration — embedding models and small models run on it perfectly well, and a vector store needs no model at all. The danger was never the CPU; it was silence: pulling four gigabytes of CUDA runtime, dropping a --gpus flag, getting two tokens a second and spending the afternoon blaming the model. So the node says what it found instead. Ollama:RequireGpu=true is there when you want the guarantee rather than the report — with no visible device it then fails startup naming --gpus all.

The node keeps its own Ollama alive

The container runs two processes: the node as PID 1 and ollama serve as its child. There is no s6, no supervisord and no entrypoint script — the v3.4 supervisor already knew how to do this job, and it turns out an init system is what it was. It starts Ollama at boot, probes it every 15 seconds on a short deadline of its own, and restarts it when it dies or wedges, under a budget that gives up loudly rather than looping forever.

That matters more in a container than on a host, because nothing else in there is watching: a wedged Ollama leaves the container looking alive, /health answering, and every request hanging. Verified the only way it can be — by killing the process inside a running container and watching the node bring it back.

What is in it, and what is not

  • ~4 GB. The plain inferhub-node image is unchanged at ~340 MB and still has no Ollama in it — a bundled flag on one image would have grown every coordinator+node stack by 4 GB for a feature it does not use.
  • amd64 and NVIDIA only. No ROCm, no Intel, no Apple; arm64 would mean Jetson-specific bundles.
  • The tag is :ollama because the image runs perfectly well without a card. :gpu is an alias for the same digest.
  • No model is baked in and none is pulled at boot. docker exec … ollama pull is the interface, and a volume at /data is required in practice — pulled models live in it.
  • Ollama's own port is not published. The container's surface is InferHub's API, which requires a key. -e OLLAMA_HOST=0.0.0.0 -p 11434:11434 is yours to decide.
  • Every OLLAMA_* variable passes through — the supervisor spawns a child that inherits the environment, so OLLAMA_KEEP_ALIVE, OLLAMA_NUM_PARALLEL and the rest need no configuration surface of ours.
  • On Windows with Docker Desktop this works through WSL2. Note that /dev/nvidia* does not exist there — InferHub detects the GPU by loading the driver rather than by looking for device nodes, so a passed-through card is found either way.

It is also a good mesh node: set Coordinator__Url instead of Coordinator__Enabled=false, and the hub can pull models into it from the console, because the Ollama it manages is genuinely its own.

docker compose -f deploy/docker/compose.ollama.yml up -d

What a node is for v3.8+

Until v3.8 a node advertised a list of model names, and the coordinator routed on that alone. That is a routing key with one dimension, and it quietly assumes every model on a node does the same kind of work. It does not: a box holding only nomic-embed-text was a perfectly good candidate for a chat request naming that model, and the error came back from the backend, after a dispatch.

Since v3.8 a node also declares capabilities — what it can do — and the unit of routing is the pair (capability, model).

curl -s localhost:5080/api/status | jq .capabilities
# [ { "capability": "chat",  "nodes": 2, "models": ["llama3.2", "qwen2.5"] },
#   { "capability": "embed", "nodes": 3, "models": ["llama3.2", "nomic-embed-text", "qwen2.5"] } ]

curl -s localhost:5080/v1/models | jq '.data[] | {id, capabilities}'
# { "id": "nomic-embed-text", "capabilities": ["embed"] }

Nothing is guessed

Ollama does not say what a model is for, and inferring it from the name — "it has embed in it" — would be a lookup table that is built, believed, and wrong for somebody. So a node declares chat + embed over everything its backend reports, and the one thing it cannot work out for itself is one line of configuration:

"Node": { "Capabilities": { "Disabled": ["chat"] } }

That node is then never sent a chat job. The key is subtractive only: you can narrow what a node is used for, you cannot make it claim something it has not got. Disabling both chat and embed fails startup, because a node routed for nothing is a machine burning power for nothing.

A capability nobody has is a 503, not a 404

If the model is on the fleet but no node will do this with it, the answer is 503 with Retry-After, naming the capability — deliberately the same shape as "every node is busy", because it is the same kind of fact: a statement about the fleet right now rather than about what exists. A model that genuinely is not on the fleet is still the 404 it has always been. The check runs after admission, so it can never be used to discover which models live behind a scope you were not granted.

Solo mode enforces the same key

Node:Capabilities:Disabled means the same thing on a standalone node: same 503, same Retry-After, both dialects. Only the enforcer moves, from a router that is not there to the node that is — a key honoured in one deployment and silently ignored in another would be worse than the asymmetry. Its own corpus is exempt, so solo RAG still embeds with embed disabled: a node's own documents are not somebody sending it work.

Upgrading

Nothing to do. A node that declares no capabilities — every node before v3.8 — is read as chat + embed over everything it reports, which is exactly the old behaviour, so a v3.7 node against a v3.8 coordinator registers and serves normally and a fleet can be upgraded one box at a time.

This is the seam the next releases need: a node that runs a speech model, or anything else that is not a language model, has to be able to say so before anything can be routed to it.

Tools on a node v3.9+

A tool worker is a child process a node starts, supervises, talks to over a line protocol, and restarts when it dies.

It is how a node does work its inference backend cannot — transcription, speech, OCR, whatever you write. It is off by default, it added zero dependencies, and v3.9 ships no tool: the machinery is proven against a worker that echoes, so Whisper and Piper land in v3.10 onto something that already works.

{
  "id": "whisper",
  "capabilities": [ { "kind": "transcribe", "models": ["whisper-small"] } ],
  "command": ["/opt/inferhub/venv/bin/python", "-u", "/opt/inferhub/tools/whisper_worker.py"],
  "env": { "HF_HOME": "/data/tools/hf" },
  "maxWorkers": 1
}
"Tools": { "Enabled": true, "Allowed": [ "whisper" ] }

The node then declares transcribe, the coordinator routes (transcribe, whisper-small) to it, and it is reachable the same way on a hub and on a standalone node:

curl localhost:5080/api/tools/transcribe -H "Authorization: Bearer $KEY" \
  -F model=whisper-small -F file=@meeting.m4a

The worker author's document is python/README.md — the protocol, the manifest reference, and exactly what the node does when a worker misbehaves. python/inferhub_worker/ is a ~150-line reference implementation you copy or vendor; it is deliberately not a package.

Why a subprocess and not a library

Because the libraries are Python, and the obvious move — Python.NET, CSnakes, an embedded interpreter — is a native binding. It pins the node to a CPython ABI; it forecloses the tool that is a Go binary or an ffmpeg invocation; and, the one that would have hurt, one bad import takes the node down. A segfault in a native extension loaded into this process is not an exception you catch, it is a process that vanishes mid-stream taking every in-flight inference job with it. A child process that segfaults is a log line and a restart.

So the node knows how to start a process, write a line, read a line and kill it. It does not know what Python is.

Opt in twice, because the second key is a ceiling

Tools:Enabled consents to the feature existing. Tools:Allowed names the manifest ids that may actually run — a manifest on disk that is not in the list is loaded, logged and never started. The two are not redundant: v3.11 lets a coordinator turn a node's capabilities on and off, and Tools:Allowed is the ceiling it can never raise. One switch would collapse "the operator enabled tools" and "the hub may run any tool present on this box" into a single consent. Naming tools while Tools:Enabled is false fails startup rather than doing nothing quietly.

This is not a sandbox

Said plainly, because the alternative is implying safety by listing mitigations. A worker runs as the node's user, with the node's filesystem and the node's network.

What the node does do is refuse to hand over its own environment: a child normally inherits the parent's, so it is cleared and rebuilt — PATH, HOME, LANG, LC_ALL, TMPDIR, USER, SHELL, whatever the manifest's env names, and nothing else. Coordinator__EnrollmentSecret does not reach a worker. That is a real hole closed and it is the honest extent of the isolation.

A tool you did not write and did not read has your box. If you want real isolation, run the tool in its own container and point a manifest at it: a "process" that is docker exec is still a process, and the protocol does not care.

Two smaller containments come with it: command must be an argv array (a string is refused by name, because every shell and every Docker CMD accepts one), and nothing from a request ever reaches the argv — model, options and file paths all travel in the protocol, on stdin, after the process is already running.

The restart budget is lifted from the v3.4 Ollama supervisor rather than re-derived, and the withdrawal reuses the mechanism a broken backend already uses. No new health field was invented.

Bytes go through files, not the pipe

Attachments are written to a per-request scratch directory and the frame carries a path; the worker writes its output beside it and names it back. Base64 over stdio was declined: it is 4/3 the bytes and materialises the payload as a string in both runtimes at once — a 25 MB audio file becomes ~33 MB of .NET string plus ~33 MB of Python str plus the decoded copies — for a handoff both sides' libraries would rather do with a path.

The scratch directory is deleted in a finally: after success, and after every failure. Nothing a request carried outlives it, and nothing containing it is logged. A worker that names an output file outside its own scratch directory is refused and logged. Attachments are capped at 25 MB (Tools:MaxAttachmentBytes), enforced at the edge as a 413 naming the limit.

Uploads larger than 25 MB v3.21+

A large body streams through the coordinator instead of landing in it.

Until 3.21, anything you uploaded was read into the hub's memory in full, capped at 25 MB by Tools:MaxAttachmentBytes, and forwarded to a node as bytes on the job. Set Tools:MaxStreamedBytes on the coordinator and on a node, and a body past that cap takes a second path: the node pulls it over the connection it already opened, 64 KB at a time, straight into the scratch file its worker is about to read. The hub holds one window and never the body, so its memory does not grow with the upload and backpressure reaches your TCP window for free.

The node pulls rather than the hub pushing, which is what keeps the mesh's outbound-only property intact: the stream is established by the node's own call on the connection it opened, exactly as its profile pull is. No inbound port appears on a GPU box.

curl -X POST http://hub:5080/v1/audio/transcriptions \
  -H "Authorization: Bearer $KEY" \
  -F model=whisper-small \
  -F file=@lecture.m4a          # 380 MB

It is off by default (0). With it off, 3.21 behaves byte for byte as 3.20 did — the same 413, from the same key, in the same words.

Three things to know before you turn it on

  • A streamed job is not retried on another node. The body has been read, it is past the hub and into a node that just died, and a client's socket cannot be rewound — so a node lost mid-upload is a 502 naming node_lost and you decide what to do. This is a real step down in reliability, on a path you opt into by size, and we would rather write it here than have you find it during an incident.
  • Send your form fields before the file part. The request is routed before the bytes arrive — that is what makes streaming possible — so a model that turns up after the file is a 400 that says so, and a field after the file is refused rather than quietly dropped. curl -F model=… -F file=@… and the OpenAI SDKs already send fields first. A solo node has nothing to route and accepts any order.
  • A fleet with no capable node answers 503 naming that reason. Support is declared per node, and a node older than 3.21 is read as "no", so a mixed fleet keeps working — buffered traffic still routes everywhere. It never falls back to buffering, because that would work brilliantly right up to the 25 MB it cannot do.

One key, three ceilings

Raising our cap alone never worked, because two of the three limits between a client and a worker belong to ASP.NET: Kestrel's MaxRequestBodySize is 30 000 000 bytes (the 25 MiB cap clears it by about 3.7 MB) and the multipart body limit is 134 217 728. Tools:MaxStreamedBytes now derives both, on the upload routes only — a global raise would also un-bound /api/chat and the vector data plane, which have no business accepting a 300 MB body.

Where it applies

POST /api/tools/{capability} and POST /v1/audio/transcriptions, on the coordinator and on a solo node. The image routes keep the 25 MB cap, and that is a decision rather than an omission: a body can only stream while somebody is waiting for it, and an image job is answered before it runs — POST /api/images/jobs returns 202 immediately, and /v1/images/edits stops waiting at Images:SyncMaxWaitSeconds while the job keeps going. Either way the bytes would have to outlive the request that carried them, which means keeping them on the hub — the image store this project has refused three times.

A correction

The note behind the old ceiling said the uploaded bytes were held in memory with no temp file, no cache. That was true of the code we wrote and false underneath it: ASP.NET's form reader spills any file part over 64 KB to a temp file. Measured on .NET 10 — a 32 KB upload creates none, a 3 MB upload creates one of 3 145 570 bytes. Nothing was retained past the request and nothing was logged, so no data outlived a call; but the claim was wrong, and it is corrected here rather than quietly edited. The streamed path does not do this, and the test suite asserts that a 40 MB upload leaves no temp file behind.

The worker protocol did not change by one field: a worker has always been handed a path into a per-request scratch directory rather than bytes, so anything written against v3.9 runs unmodified.

Speech that starts before it is finished v3.37+

A paragraph is a couple of minutes of audio, and until 3.37 the socket was silent for all of it: the whole input was synthesised, written to a file on the node, shipped back across the wire and handed over as one body. Every product that reads text aloud — a chat UI, a reader, an IVR — starts playing the first sentence while the rest is still being made. Add OpenAI’s own stream_format and the samples arrive as they are produced, one piece per sentence:

curl -N http://localhost:5080/v1/audio/speech \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"model":"en_US-amy-medium","input":"One. Two. Three.","response_format":"wav","stream_format":"audio"}' \
  --output out.wav

  ... "stream_format":"sse"
#   event: speech.audio.delta   {"type":"speech.audio.delta","audio":"<base64>"}
#   event: speech.audio.done    {"type":"speech.audio.done","usage":{"input_tokens":0,...}}

Leaving stream_format out changes nothing. The response is byte for byte what 3.36 returned, on a hub and on a standalone node alike. Both of OpenAI’s values are served, and audio is the one an SDK actually consumes — their own Python client models neither streaming event, so sse is a documented-but-unmodelled surface and with_streaming_response.create(...).iter_bytes() is what a client already knows how to do.

wav, pcmstream
mp3, opus, flac400 naming the two that do

Concatenability is the whole contract. The encoded formats need ffmpeg alive for the length of the request and a chunk boundary that is not a codec frame boundary — a naive split clicks every third of a second. The refusal is a 400 rather than a quiet fall back to buffering, because a caller who asked to stream and silently got a two-minute wait has a bug with nothing in the response to explain it.

Four things a client should know

  • A streamed wav carries 0xFFFFFFFF in both length fields. The header is 44 bytes written once, from the first chunk, and the length is simply not knowable then. Players accept the sentinel; ffprobe will report a nonsense duration.
  • The sample rate is on X-InferHub-Audio-Sample-Rate, measured from the audio rather than declared — Piper knows its own rate only from its own first samples, and a hand-set one plays at the wrong pitch while passing every byte-count assertion anybody writes. For pcm that header is the only place the rate can be, which is also why the status is not committed until the first chunk lands: a refusal is still a 400 or a 502 with an ordinary error envelope.
  • The usage in speech.audio.done is three zeros, and they are true. The schema requires the object so it is written; Piper is a phoneme model and nothing was tokenized. What is metered is unchanged since 3.10 — input characters, also on X-InferHub-Speech-Characters. Putting a character count in a field named tokens would be roughly a four-to-one error landing on somebody’s invoice.
  • speech.audio.error is ours. OpenAI’s schema defines only delta and done, and a stream that dies after the first byte has no status left to send — so sse ends with a terminal event carrying the ordinary envelope, and audio closes, because there is nowhere in a raw byte stream to put a sentence. Closing silently leaves a client unable to tell an ending from a failure.

A mixed fleet keeps working, and one number is load-bearing

Nodes declare whether they speak this contract. A pre-3.37 node keeps serving every buffered request it always did and is simply not a candidate for a streaming one; a fleet with none new enough answers 503 naming the version rather than “no node provides speak”, which would send an operator to look at their voices.

The other half is the one 3.10 paid for. SignalR’s default receive limit is 32 KB and exceeding it does not fail the message — it kills the connection, which is how v3.10.0 shipped dead on arrival: a six-second wav is ~300 KB, so every real speech request dropped the node and made it re-register. A streamed answer crosses that wire fifty times instead of once. So the worker splits at 16 KiB of PCM — ~21.8 KB once base64 and the frame are on it, under SignalR’s own default, so a hub whose operator never raised a limit is safe — and the node refuses to forward anything larger, ending the job with both numbers in the sentence rather than dropping the connection. The worker is retired when that happens: the stream is abandoned without telling it, so its remaining frames sit on the pipe against a request that no longer exists, and a warm worker would hand them to the next caller as their answer.

What has not been established: no real Piper voice has streamed yet and nobody has listened to one. That synthesize() yields a chunk per sentence is read out of the pinned library’s own source; the tests drive the echo worker. Time to first audio has not been measured.

None of it is kept

The retention rule at its most literal: a transcription request is a recording of somebody's voice, and the answer is what they said.

  • The hub buffers the upload for the dispatch and drops it. No temp file, no cache.
  • The node writes it into a per-request scratch directory deleted in a finally — after success and after failure.
  • Nothing containing audio bytes or transcript text is logged, at any level. The line for a transcription carries the model, the duration and the outcome. Not even the filename you chose: board-meeting.m4a is metadata about somebody's day and is not needed to run a fleet.
  • The usage ledger gains a duration, never a transcript.

The test runs a transcription through a real mesh with a capturing logger and fails if a known phrase from the fixture appears anywhere in the log or the ledger.

Metered in the unit the work is actually in

Audio has no token count, so metering it as tokens would mean inventing a number. A usage row now carries units and a unitKind — tokens, audio_seconds or characters. The token fields are untouched, the Postgres migration is additive and rewrites nothing, and a row written by v3.9 still means exactly what it meant.

"Limits": { "AudioSecondsPerDay": 3600, "CharactersPerDay": 200000 }

Separate budgets, each consuming only its own unit — a client whose only limit is TokensPerDay could otherwise transcribe a library for free. Over one is the same 402 + Retry-After to UTC midnight as the token budget, in the OpenAI envelope on /v1.

A busy transcription does not slow your chat

maxWorkers defaults to 1: a second Whisper process on the same card is two copies of the weights and an out-of-memory error at the worst possible moment. But because routing has been per (capability, model) since v3.8, a node busy transcribing is still a candidate for chat — with a 113-second transcription running on one node, a chat request answered on another in 1.5 s. That is the earlier release paying for itself, and it is worth stating because nobody can see it working: the failure it prevents is "my chat got slow when someone uploaded a podcast".

Deliberately not in this release

Diarization, alignment and voice cloning — verbose_json carries the segments and timestamps Whisper produces anyway, and speaker labels it does not produce are not invented. /v1/audio/translations — one flag on the same worker, and it can land whenever somebody asks; shipping an untested surface to look complete is how a feature list starts lying.

Quantization is a property of the model, not of the request v3.16+

"quantization": "none" | "int8" | "nf4" in the recipe, through diffusers' native bitsandbytes integration, applied to the components the recipe names. For qwen-image that has to include the text encoder: 8.3B left at bf16 is the difference between fitting on a 24 GB card and not.

It is a recipe field rather than a header because it changes what the model is. Two requests to qwen-image that quantized differently would produce different images from the same seed, and a per-request knob would make reproducibility a function of a header nobody logged. Want both? Ship two recipes with two ids — which is honest, and is also how you will describe it to your users.

One mechanism, deliberately. GGUF, Nunchaku and TensorRT are each faster on some model on some card, and each is a second thing to reason about when a picture comes out worse than expected.

Weights arrive by an explicit pull v3.16+

FLUX is ~24 GB on the wire and Qwen-Image is larger. A lazy first-use download blows requestTimeoutSeconds — 3.14.0 shipped exactly that, and every first sdxl call was a 502 after 899.99 seconds — and raising that timeout to cover a 24 GB download means every genuinely wedged job also takes forty minutes to fail. So a pull is an operator action, on the model-command channel the fleet has had since 2.8:

POST   /api/admin/nodes/{nodeId}/tools/diffusion/models/flux-schnell/pull
DELETE /api/admin/nodes/{nodeId}/tools/diffusion/models/flux-schnell

Progress relays on the existing /api/admin/stream as model-progress — no new transport — and the coalescing, the reused command id and the "a hub restart forgets in-flight commands" property all come with it. The progress carries no percentage: huggingface_hub gives no download callback, and a denominator we would have to guess is a number a dashboard would happily plot. It reports how many mebibytes have landed instead. A generation request for a recipe whose weights are absent is a failed job naming both that command and the huggingface-cli one — never a forty-minute wait.

Switching models swaps weights; it does not restart anything v3.16+

Loading FLUX is 40–90 seconds, and a restart pays the interpreter and the import of torch on top of that, on every alternation. So the worker frees the old pipeline, empties the cache, loads the new one, and reports the swap in the result's timing block — a slow request has a visible reason rather than being the one somebody remembers as "it was slow that time".

Tools:Image:ResidentRecipes (default 1) allows more than one resident where the budget permits: a 48 GB card genuinely can hold SDXL and FLUX together and should not thrash. The default is 1 because the expensive default is the one nobody realises they chose. After idleTimeoutSeconds the node sends an idle hint and the worker frees its VRAM and stays alive — what to free is the worker's business, because the node knows nothing about torch.

X-InferHub-Image-Seedany non-negative integer — also accepted as "seed" in the body

negative_prompt is a body field, deliberately: it is your own words, and a header is the one part of a request every proxy in the path writes into a log. Every returned image carries the seed that produced it, so the one of four you liked is reproducible without re-rolling the other three.

Weights arrive in the background, and a model appears when it is ready

On a fresh volume the node starts with nothing declared and fills in as each model lands:

[diffusion] offering recipes: none yet (fetching: sd15, sdxl)
[diffusion] fetching weights for 'sd15' from stable-diffusion-v1-5/…@451f4fe16113 (variant=fp16)
[diffusion] 'sd15' is ready; offering recipes: sd15
[diffusion] 'sdxl' is ready; offering recipes: sd15, sdxl

No request ever waits on a download, and the fleet never routes at a model that is not there — the node tells its coordinator the moment one becomes available, without a restart. Measured on a clean volume: the node answers in 2 s, sd15 is serving about a minute later and sdxl at 3½ minutes, for 8.7 GB of weights.

That is v3.14.1, and v3.14.0 got it wrong: it fetched inside the request that first named the model, so the first sdxl call on a fresh volume spent the whole 900-second request budget downloading and returned a 502. Found by pulling the published image and running it, which is the only way that class of thing is ever found.

360° panoramas v3.17+

qwen-360 is ProGamerGov/qwen-360-diffusion — a rank-128 LoRA, MIT licensed, over Qwen-Image's 20B MMDiT. It produces equirectangular panoramas: 360° of longitude across, 180° of latitude down, left edge continuing into the right.

curl http://localhost:5080/api/images/jobs \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"model":"qwen-360","prompt":"a Bulgarian mountain monastery courtyard at golden hour, photograph","size":"2048x1024"}'

Once it succeeds, every image carries what it is:

{
  "created": 1785000000,
  "data": [{ "b64_json": "iVBORw0…", "size": "2048x1024", "seed": 42,
             "projection": "equirectangular", "seam_delta": 0.014, "revised_prompt": null }],
  "prompt_augmented": true,
  "trigger": "360 degree panorama with equirectangular projection"
}

A 2:1 aspect is not a suggestion. 360° over 180° is exactly two to one. A size outside a flat recipe's buckets gives you duplicated limbs — visibly bad, and everybody knows what happened. A non-2:1 equirectangular render looks perfectly fine and wraps wrongly, and the person who discovers that is wearing a headset three days later. So it is a 400, and unlike every other size refusal it says why.

The trigger phrase is appended, not demanded and not silently inserted. The model wants "equirectangular" or "360 panorama" in the prompt. Rewriting yours silently is the one thing nothing here does; refusing a prompt without it would make the first request everybody sends a 400. So it is appended when absent and the response says so — prompt_augmented, plus the phrase. "autoTrigger": false in the recipe turns it off, and the flag is reported either way, so a client never has to infer what happened to its own prompt. The trigger is a recipe constant, so unlike your prompt it may appear in a log — which matters, because "why does this not look like a panorama" is almost always "the trigger did not apply".

The seam is measured on every panorama, and repaired only if you ask. seam_delta is the mean absolute difference between the first and last columns — the pair that becomes adjacent once the image is wrapped onto a sphere — normalised to 0–1. Over Tools:Image:SeamWarnThreshold (default 0.08) the result carries "warnings": ["seam"]. A warning on a 200, never a failure: a slightly visible seam is your own problem and your own aesthetic judgement.

Since 3.23 you can close it — through two gates. We measured this flaw for six releases and refused to fix it, because a repair you did not ask for is a second generation pass you did not watch and would be billed for. What changed is the asking. The operator sets Tools:Image:SeamRepair on the node — off by default, then blend, diffuse or any — and the request picks within that:

curl http://localhost:5080/v1/images/generations \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -H 'X-InferHub-Image-Seam-Repair: blend' \
  -d '{"model":"qwen-360","prompt":"a lighthouse at dusk","size":"2048x1024"}'

# 200  "seam_delta": 0.011, "seam_delta_before": 0.134, "seam_repair": "blend"

Nothing repairs by default, and no threshold ever triggers one. The threshold decides whether to warn; a number that decides to spend your GPU is the tool overriding you with a helpful expression on. Send no header and the response is what 3.22 sent, byte for byte.

  • blend is a wrapped feather across the join: numpy on the array the VAE already produced — milliseconds, no VRAM, no steps and nothing on your bill. It closes a tonal discontinuity and not a structural one: a seam through a doorway comes back with no visible step in brightness and the doorway still not lining up.
  • diffuse rolls the join into the middle of the picture and inpaints a band of it — upstream's fix_seam, over the same resident weights. It costs int(steps × 0.4) more steps, metered in megapixel_steps and included in total_steps from the first progress frame, so the bar never restarts.

diffuse does not imply blend: these name mechanisms rather than tiers, so an operator who thinks a feathered band is worse than an honest seam can permit only the real repair. any is how you say both. A repair that does not lower the number is discarded and says so — you get the original image, the mechanism, and two equal numbers, because a pass that quietly made your panorama worse is the one outcome nobody would ever go looking for. seam_delta is always the image you were handed; seam_delta_before is what it measured first. On the content route the same three facts arrive as X-InferHub-Image-Seam-Repair, -Seam-Delta and -Seam-Delta-Before.

Honest about what was verified: the mechanisms were built and tested against synthetic rasters and the pinned diffusers mapping was read out of the wheel, but no repaired panorama has been rendered on a card for 3.23. A synthetic seam is a unit test, not evidence.

Projection is metadata, and it reaches you on every surface. A 2048×1024 panorama and a 2048×1024 landscape photograph are the same bytes in the same shape, and every viewer on the internet guesses from the aspect ratio — which is wrong for both of them. So the worker declares it: on each image in the response body, on the job document, and as X-InferHub-Image-Projection on GET /api/images/jobs/{id}/content/{index}, which is the one request with no JSON to carry it. A flat recipe reports "flat" rather than omitting the field — an absent projection is indistinguishable from a node too old to have an opinion.

Loading the viewer…

qwen-image and qwen-360 are two model ids over one base, not one model with a scale parameter. The router keys on (capability, model) and nothing else, so a client asking for qwen-image must never receive a panorama — and a loraScale header would make what you get depend on a header, which is the reproducibility problem quantization is already a recipe field to avoid. You need a card, and this says so rather than being quietly slow

Unset it and only recipes marked cpuViable are offered — sd15 at 512×512, and not sdxl. Tools:Image:AllowSlowCpu=true offers the rest anyway: your hardware, your call. No URL, no gallery, no prompt in a log

A prompt is content. A transcript is content because it is what somebody said; a prompt is content because it is what somebody wanted, and the picture is the answer — which makes an image request the most revealing thing a caller sends a fleet.

  • response_format=url is a 400 naming b64_json. Serving a URL means the hub keeps the bytes, and keeping the bytes means an image store, a retention window and a question about whose pictures those are that we have not agreed to answer.
  • Nothing logs a prompt, at any level, on either host. The line for a generation carries the model, the image count, the megapixel-steps and the outcome.
  • The node writes images into a per-request scratch directory deleted in a finally — after success and after failure.
  • There is no bundled safety classifier, and that is a decision: the one diffusers ships returns a black image, which is indistinguishable from a broken VAE, a bad seed or an out-of-memory error, so the operator gets a bug report instead of a policy signal. This box generates what you ask it to generate; the policy is yours.

Batches are bounded by bytes, not by count

n is capped by Images:MaxBatch (4) and by an upper-bound byte estimate checked before a step runs, with the refusal naming the largest n that fits at that size. The budget is clamped by Tools:MaxAttachmentBytes, because that cap is what sizes the mesh's SignalR message limit — and exceeding a SignalR limit tears the node's connection down rather than failing the message. Raising one without the other gets you no change, deliberately.

A batch runs on one node: fanning it across the fleet would mean four different seeds' worth of scheduling for a request you think is atomic, and a partial failure would have no honest status.

Metered in megapixel-steps

width × height × steps / 1e6, from what the worker actually produced. Not "images": a 512² render at 4 steps and a 2048×1024 one at 30 steps are both one image, and the second is 47× the work.

"Auth": { "Clients": [ { "Id": "acme", "Key": "…",
  "Limits": { "MegapixelStepsPerDay": 5000 } } ] }

Over it is a 402 with Retry-After pointing at UTC midnight, the same shape as every other budget.

Editing a picture v3.18+

Inpainting, image-to-image and variations — on OpenAI's edits API, multipart and all.

curl http://localhost:5080/v1/images/edits -H "Authorization: Bearer $KEY" \
  -F model=sdxl -F image=@room.png -F mask=@mask.png \
  -F prompt="a tall window with morning light" \
  -H 'X-InferHub-Image-Strength: 0.75' \
  | jq -r '.data[0].b64_json' | base64 -d > edited.png

Three shapes, and the difference between them is what you send:

RouteSendsIs
POST /v1/images/edits with a maskimage + mask + promptinpainting — the masked region only
POST /v1/images/edits with no maskimage + promptimg2img — the whole picture, strength far
POST /v1/images/variationsimagemore of this picture, no prompt at all

The mask convention everybody gets backwards

OpenAI's edits API treats a fully transparent pixel as the area to edit. diffusers takes a mask where white is the area to inpaint. These are opposite.

Get it backwards and nothing errors. It edits everything except what you selected, which reads as a broken model rather than a backwards mask — and you find out by looking at the picture. So there are two refusals rather than a guess:

  • A mask with no alpha channel is a 400. Under OpenAI's convention a fully opaque image selects nothing, which nobody has ever intended. Reading it as "edit everything" would be a silent substitution of the most destructive possible interpretation; reading it as "edit nothing" would hand you your own picture back with a 200 on it.
  • A mask whose size differs from the image is a 400 naming both. A mask names which pixels, so it is never rescaled — the edit would land next to what you chose.

Already have a white-is-edit mask? Say so with X-InferHub-Mask-Convention: luminance. An unknown value is a 400 that names both and says which is which, because two words whose difference is invisible until you look at the result are not a helpful list.

The conversion happens in the worker, and that is a constraint rather than a convenience. Turning one convention into the other means reading an alpha channel out of a PNG — and nothing in InferHub's C# ever decodes a pixel. There is no image library on the hub, by design, so the shared library owns what the conventions are and the inversion happens where PIL already is. The cost is one round trip to find out a mask is wrong, which is the same trade this project took for aspect buckets in 3.14 and for the 2:1 refusal in 3.17.

Strength is a header, and you are billed for the steps that ran

OpenAI's edits API has no strength, and image-to-image without one is meaningless — it is the whole knob. X-InferHub-Image-Strength takes 0–1: 0 keeps your picture, 1 ignores it. Absent, the recipe's defaults.strength applies (0.75 for both editable recipes); out of range is a 400.

diffusers enters the schedule at int(steps × strength), so 30 steps at 0.6 denoises for 18 — and 18 is what the worker reports, what the progress frames count up to, and what the ledger gets. Billing the asked-for 30 would charge for work nobody did.

Not every model can edit

Editing is its own capability, image-edit, declared per recipe from an operations field: sdxl and sd15 do generate, edit, variation; everything else does generate. FLUX.1-schnell has no official inpainting pipeline and SDXL does. So an edit against a generate-only recipe is a 503 that names the ones that can:

{ "error": { "code": "capability_unavailable", "message":
  "no node currently provides 'image-edit' for model 'flux-schnell'. Models on this fleet that do: sd15, sdxl" } }

That is fleet state, not authorization — the distinction 3.8 wrote down. And it is a second capability kind rather than a per-model operation list, because the router filters on (capability, model) and nothing else: teaching it to read a nested operation set would mean teaching the affinity, the queue and the saturation logic the same thing. The same model still generates — a capability refusal that took a model offline entirely would be a much bigger claim than the one being made.

An edit is a job like any other

Same queue, same per-step progress, same cooperative cancel, same five-minute retention, same read-once collection. The async route takes multipart too, and names its operation:

curl http://localhost:5080/api/images/jobs -H "Authorization: Bearer $KEY" \
  -F operation=edit -F model=sdxl -F image=@room.png -F mask=@mask.png \
  -F prompt="a tall window with morning light"

JSON generates; multipart edits. A multipart submission that names no operation is a 400 naming both — this is InferHub's own contract, where ceremony is cheaper than a silent substitution. It is not the background: true flag 3.15 refused: that one made a single route answer two incompatible response shapes depending on a field, and here the response is the same job document either way while the request shape is decided by Content-Type, which is what content types are for.

What comes in is content too

Every attachment InferHub had ever moved went node → hub. An edit is the first thing that sends megabytes the other way, so the release carries that assertion in the direction nobody had tested: a 3 MB input image crosses a real SignalR connection and the node is still registered afterwards, and still serving.

  • Images:MaxRequestBytes (25 MB) caps the picture and the mask together — a 413 at the edge, before anything is buffered onward. Each part is additionally capped by Tools:MaxAttachmentBytes, because that is what the node enforces and a request that passed the edge and failed at the node is a worse error.
  • The filename you chose never leaves the edge. The parts travel as image and mask: what you called a file on your disk is metadata about your day.
  • Nothing is retained — the bytes are held for the dispatch, written into a per-request scratch directory the node deletes in a finally, and dropped.

Not in 3.18, and said out loud: ControlNet, IP-Adapter and reference-image conditioning (each is a per-base-model zoo of auxiliary weights with its own preprocessors, and every preprocessor is image processing); an outpainting helper (it is inpainting with a canvas you prepare, and preparing it on the hub would mean decoding a pixel); multi-image edit chains; and FLUX inpainting, which has no official pipeline to wrap.

A job that takes two minutes v3.15+

An SDXL render at 50 steps is not a request, it is a job. Before v3.15 you sent one and held a connection open, and the only two things you could learn were "it worked" and "something timed out" — usually from a proxy in the path, with a status nobody could act on.

# submit
ID=$(curl -sS http://localhost:5080/api/images/jobs -H "Authorization: Bearer $KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"sdxl","prompt":"a lighthouse in a storm","size":"1024x1024"}' | jq -r .id)

# watch  (SSE: queued → running(step 7/28) → succeeded)
curl -N http://localhost:5080/api/images/jobs/$ID/events -H "Authorization: Bearer $KEY"

# collect (read-once, in memory, expiring)
curl -sS http://localhost:5080/api/images/jobs/$ID/content/0 -H "Authorization: Bearer $KEY" -o out.png

# or change your mind
curl -X DELETE http://localhost:5080/api/images/jobs/$ID -H "Authorization: Bearer $KEY"

A submitted job answers 202 with a place in line, not a wait-then-503: you already accepted asynchrony, so making you retry would be strictly worse than telling you where you are.

The state machine is a table both hosts and the tests read from the same place:

            ┌──────────┐
   submit → │  queued  │ ──────────────────────────► cancelled   (nothing spent)
            └────┬─────┘
                 │ a capable node is free
                 ▼
            ┌──────────┐   DELETE    ┌────────────┐
            │ running  │ ──────────► │ cancelling │
            └────┬─────┘             └─────┬──────┘
                 │                         │
      ┌──────────┼──────────┐        ┌─────┴──────┐
      ▼          ▼          ▼        ▼            ▼
 succeeded    failed    expired   cancelled   succeeded   ← legal, and not a race
      │                                          │           to paper over
      └────────── read once, or 5 min ───────────┴──► expired

The transition that looks like a bug and is not is cancelling → succeeded. A job cancelled at step 27 of 28 may finish anyway, and if it does you get your image — discarding a real result to honour a state name would be worse than telling you what actually happened.

There is no background: true flag

OpenAI has no asynchronous Images API to adopt, and where there is no dialect to adopt this project does not invent an OpenAI-shaped one — work with no existing shape travels as its own contract under /api. A flag on /v1/images/generations returning a non-OpenAI body would make one route answer two incompatible shapes depending on that flag, which every typed SDK gets wrong, and would turn "is this endpoint OpenAI-compatible?" into a question with a footnote.

/v1/images/generations is unchanged. Internally it became "submit a job and wait for it", so a synchronous call and an asynchronous one queue in the same line and are metered by the same code — two paths to a GPU with two ideas of fairness is how a fleet grows a fast lane nobody documented. Past Images:SyncMaxWaitSeconds (120) it answers 503 naming the job id and the async route, and the job keeps running: throwing away a minute of GPU because an HTTP client got bored is your decision, not the hub's.

Cancel does not kill the worker

A DELETE sends a cancel frame down to the worker, which honours it from its per-step callback and answers with an error coded cancelled. Then it is still alive and still holding its weights, so the next job starts without reloading them.

Killing it would be simpler and is wrong. A diffusion worker's weights took tens of seconds to load — twelve to twenty gigabytes taking a minute or more once the catalogue grows — so killing it to abandon one job punishes the next caller, and the punishment gets worse with every model added. A worker that has not answered within Tools:CancelGraceSeconds (20) is by definition not cooperating, and that one is terminated and restarted.

Results live for five minutes, in memory by default

  • Images:Jobs:RetentionSeconds (300) — a finished job's record and bytes are dropped this long after completion, read or not.
  • Images:Jobs:MaxRetainedBytes (512 MB) — a global ceiling, LRU-evicting completed results and never an in-flight one, enforced on insert rather than on a timer. A timer means the ceiling is a suggestion for one sweep interval, and one sweep interval of 4096² batches is how a hub gets OOM-killed.
  • Read-once by default. A delivered image is dropped immediately; a second GET is a 410 that says why, not a 404 that reads like a bug. Images:Jobs:KeepAfterRead exists for a console's benefit and is documented as the setting that makes the hub briefly an image cache.
  • Nothing touches disk by default. No temp file, no spill under memory pressure, no cache directory. Under pressure the answer is eviction and a 503 on submit, not a file — and a restart forgets in-flight and completed jobs, exactly like every other counter on the hub.

A job can survive a restart, if you say so v3.24+

Until v3.24 a deploy turned a job id from thirty seconds ago into a 404 — byte-identical to an id that never existed, which reads as a bug. Images:Jobs:Persistence=file writes a finished job's record and its bytes under Images:Jobs:DataDirectory, so it does not.

docker run … -e Images__Jobs__Persistence=file -v inferhub_data:/data …
# the images already point Images__Jobs__DataDirectory at /data/images

It is off by default, and that is not caution for its own sake. This is the fourth recorded exception to the "no persisted state" rule and the only one that stores user content: turning it on is answering a data-retention question rather than flipping a performance switch. So it was argued at the rule, and the argument is what bounds it:

  • Durability does not extend retention. The window is applied on load — a hub that was down for an hour comes back and deletes everything past RetentionSeconds before it serves the first request, rather than resurrecting it and letting the five-second sweeper catch up. Restarting is never a way to keep a picture longer than you allowed, and a resurrection would be the bug nobody finds: it happens in the crash-recovery path, on a box nobody is watching, and it looks like the feature working.
  • Read-once means read-once from the disk too. Delivery, eviction and expiry each unlink the file in the same operation that drops the bytes, so what the API says and what the directory holds cannot disagree.
  • An interrupted job is never resumed. It comes back failed with reason hub_restarted and a sentence saying so. Nothing durable holds your prompt — there is no field for one, deliberately, because a field is an invitation — and a re-dispatch would have needed it. It is the same answer a node disappearing mid-job gets, for the same reason: a silent retry spends the GPU minutes twice for one request.
  • There is no postgres here. Image bytes are not row data: half a gigabyte of PNGs in a bytea column is WAL amplification per render and a database dump that now contains pictures. Symmetry with the other two persistence keys is not a reason to put the wrong thing in a database.
  • Under clustering it is per instance. A promoted standby does not hold the old primary's pictures — the hubs share a Postgres, not a directory — and a shared filesystem is a deployment choice this project neither requires nor tests.

An unrecognised value fails startup naming the key rather than falling back to none, which would silently drop every job on the next restart — the exact failure you turned the key on to prevent. Solo mode reads the same key into the same class, so a standalone node cannot keep an image longer than a hub does.

The queue is FIFO and it is not clever

A GPU running diffusion is a resource there is exactly one of, so the hub gives each capable node one image job at a time and takes the queue in order. Shortest-job-first would let a stream of four-step requests starve a fifty-step one indefinitely and the starvation would be invisible; fair-share needs a notion of tenant weight this project's client model does not have. Images:Jobs:MaxQueueDepth (32) bounds it, and a full queue is 503 + Retry-After — the same status and header as every other limit here.

A node that disappears mid-job fails the job, and never retries it

An image job that died at step 22 produced no output, so it is technically retryable — and retrying it would silently double the GPU-minutes and the ledger units for one request. It fails with node_lost and you decide. A job still queued when its node goes away has spent nothing and is simply routed again.

Every route is yours only

A job id belonging to another client is a 404, byte-identical to one that does not exist — never a 403. On a surface whose ids are only knowable by having been issued one, the difference between "not yours" and "not there" is the isolation boundary.

Writing a worker that reports progress and honours a cancel

The protocol gained two frames, both additive — a worker written against 3.14 never sends progress, never receives cancel, and behaves exactly as it did. In the Python reference library it is two lines inside your step callback:

for step in range(1, steps + 1):
    ...
    request.progress(step, total_steps=steps)
    request.raise_if_cancelled()

One thing worth copying rather than rediscovering: the reference loop reads with readline() instead of for line in sys.stdin. The iterator protocol keeps a read-ahead buffer, and the frame two readers would lose between them is the cancel.

Solo mode gets the same five routes

A standalone node serves /api/images/jobs itself, with the same bodies and the same statuses — one job at a time, because it is a box with a card in it. The deployment least likely to have a proxy that tolerates a two-minute request is the one somebody is running on a laptop.

Deliberately not in this release

img2img, inpainting, /v1/images/edits, /v1/images/variations, ControlNet, and any model that needs quantization to fit a card. Also previews: decoding the latents each step costs 10–15% of the run and produces intermediate content, so they are off — and a release that adds them will add them with a worker that actually produces one, rather than a header whose only observable effect is more of what you already get.

Upgrading

Nothing to do. The image routes answer a 503 naming the capability until a node provides it, the job routes are mapped and inert, and a deployment that changes no config behaves identically to v3.14.

Text to video v3.25+

A short clip on your own card, through OpenAI’s Videos API — not one we invented.

curl -s http://localhost:5080/v1/videos \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"model":"wan-t2v-1.3b","prompt":"a paper boat on a puddle, slow dolly in","seconds":5}'
# {"id":"video_8f3c...","object":"video","model":"wan-t2v-1.3b","status":"queued","progress":0,
#  "seconds":5,"size":"832x480","created_at":1755400000}

# ..."status":"in_progress","progress":42...

curl -s http://localhost:5080/v1/videos/video_8f3c.../content -H "Authorization: Bearer $KEY" -o out.mp4

GET /v1/videos/{id} polls, /content fetches the bytes once, and DELETE cancels and drops it. That is the whole surface.

Why this one is adopted and the image one was invented

v3.15 built /api/images/jobs because OpenAI has no asynchronous Images API to adopt, and this project’s rule is to speak the dialect clients already speak and to invent only where there is none. Video has one, and it is asynchronous by construction — create, poll, fetch, delete — so client.videos.create(...) in any OpenAI SDK works against a hub that can serve it, and we added nothing.

Two of that dialect’s routes are 501s that say why rather than 404s that read as an old server. GET /v1/videos would enumerate your jobs and this coordinator holds no such index — the id it handed you is the capability to fetch the bytes. POST /v1/videos/{id}/remix needs the request kept after the job ends, and nothing durable here holds a prompt.

The status mapping loses exactly one distinction, deliberately: cancelling renders as in_progress, because a job asked to stop is still running and may finish. And progress is capped at 99 until the job is terminal — a client that sees 100 and stops polling has stopped one round trip before the bytes exist.

It is the same job model, so it is the same everything else

The queue, the per-step progress, the cooperative cancel that leaves the worker holding its weights, the five-minute read-once retention and v3.24’s optional durability are the code image jobs already run. Images:Jobs:* configures both and Images:MaxResponseBytes bounds both — there is no Videos: section, because two keys for one wire ceiling are two numbers you could raise independently, and exceeding the mesh’s message limit tears a node’s connection down rather than failing a message.

A video id will not open an image route and an image id will not open a video route: both are the same 404 an unknown id earns.

All three are Apache-2.0, so none of them needs a licence decision. wan-t2v-14b-720p does not fit a 24 GB card, and that is the VRAM gate working rather than a packaging mistake: a node with 24 GB never declares it, so the hub never routes to it and nobody finds the ceiling four minutes into a render. A recipe’s figure is sized at the largest (size, seconds) pair it offers, because the gate is handed one number before any caller exists — which makes a recipe id a model and a geometry. A recipe with no figure at all is still admitted if it is an image model, and not declared if it is a video one: the same silence costs an image recipe a few gigabytes and puts a 24 GB model on a 12 GB card.

cogvideox-2b is why fps became a required field. It runs at 8 where Wan runs at 16, and a worker that fell back to 16 would encode its 49 frames at twice their rate — not an error, a clip that plays at double speed from a model that then reads as bad at motion. 49 frames at 8 fps is 6.125 s, so seconds: 6 is the label and 6.125 is what comes back; anything else is refused with it offers: 6. Its own config explains the single offer: learned positional embeddings sized for one grid, and a model card that says “720 x 480, no support for other resolutions”.

Two more things v3.26 settled by reading rather than guessing. The 14B repository ships flow_shift: 3.0 too — byte-identical to the 1.3B’s, and 3.0 is the 480p value — so the recipe’s 5.0 override is the only thing between a 720p render and the wrong schedule. And vaeTiling exists because a video job’s peak allocation is at decode: the loop holds a latent, then the VAE materialises every frame at full resolution at once, after all the expensive minutes.

The first model, and four things about it worth knowing

wan-t2v-1.3b is Wan-AI/Wan2.1-T2V-1.3B-Diffusers — Apache-2.0, so no licence decision — at 832×480 or 480×832, 2 to 5 seconds, 16 fps. Every one of these was read out of the pinned diffusers wheel and the model’s own configs, because each produces a plausible non-failure when it is wrong:

  • “1.3B” names the transformer only. The text encoder beside it is UMT5-XXL at ~11B, every weight in the repo is stored fp32 with no fp16 variant, and the first pull is ~29 GB. The recipe declares 15 500 MiB of VRAM for that reason, not for 1.3B of it.
  • Sizes divide by 16, not by 8. 840x480 is a perfectly good image size and an invalid video one; the refusal happens at the edge rather than four minutes into a job.
  • seconds is a label and the response reports the measurement. A latent video pipeline puts frames on a 4k+1 grid, so seconds: 5 means 81 frames and 81 frames at 16 fps is 5.06 s — which is what comes back. A duration the model does not offer is refused naming the list, never rounded to the nearest one: asking for six seconds and silently getting five leaves you with a clip that is fine and wrong.
  • fps is not yours to set — and since v3.26 the recipe must state it. It is the rate the model was trained at; re-timing the frames at encode changes how fast the world moves. A recipe that does not declare it is skipped and logged by name rather than assumed to be 16.

Usage, and the two units

A video meters both: megapixel_steps — width × height × frames × steps / 1e6, because a video transformer denoises the whole latent stack on every step — and video_seconds. The first is the card’s real cost and spends the same MegapixelStepsPerDay budget an image does, because it is the same card: a 5-second 832×480 clip at 30 steps is about 970 megapixel-steps against an SDXL image’s 31. The second is the number a human asks about, and neither can be derived from the other. inferhub_video_seconds_total{kind,model} is on /metrics, and emits nothing at all on a fleet that has never rendered one.

What the video track does not do yet

No image-to-video — a second capability and a second input path, named rather than forgotten. No caller-chosen fps. No audio: Wan2.1 T2V produces none, and a silent track added to look complete is a lie in a container. No 480p entry for the 14B — the same weights at a second geometry means two recipe ids over one loaded pipeline, which the residency map would count twice against one card; that is a release, not a JSON file. No listing on /v1/videos — an id is the capability to fetch the bytes, so the dialect’s enumeration stays a 501 that says why and the console’s listing is a client-scoped route of our own. Video has now been rendered and watched (v3.28): a five-second 832×480 clip, 81 frames, 378 s end to end on a 3090 Ti. That release also found that none of this had ever worked on a published image — the :diffusion manifest never declared the video kind, so the node discarded what the worker offered and POST /v1/videos answered model_not_found for three releases. Fixed in 3.28, along with two packages diffusers uses and does not declare.

Upgrading

Nothing to do. The video routes answer a 503 naming the capability until a node declares it, and a deployment that changes no config behaves identically to v3.24.

Configure the fleet, not the boxes v3.11+

The coordinator says what a node should be doing. The node decides whether it may.

Twenty nodes has meant twenty appsettings.json files and twenty restarts. A node profile is one document on the coordinator that every matching node converges on:

curl -X PUT http://localhost:5080/api/admin/profiles/gpu-boxes \
  -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' -d '{
    "selector": { "labels": { "tier": "gpu" } },
    "capabilities": { "embed": false },
    "tools": { "whisper": true, "piper": false },
    "models": { "ensure": ["llama3.2"], "remove": [] },
    "maxConcurrency": 4
  }'

Each node applies what it can and reports back what it would not do and why. GET /api/admin/nodes/{id}/profile is the answer to the only question you ask afterwards — I wrote that and the box still does what it did before.

The hub can only ever narrow a node, and the check runs on the node

This is the design decision the feature exists around, and it is the one most systems in this space get the other way round.

  • A profile can switch a capability off. It cannot re-open one the box's own Node:Capabilities:Disabled closed.
  • It can stop a tool. It cannot introduce one — a tool id that is not already in that node's Tools:Allowed is refused by name, and there is no field anywhere in a profile for a command, a path or an interpreter. That is why v3.9 made that key a list rather than a second boolean: it was always going to be the ceiling this release could not raise.
  • It can lower MaxConcurrency. Raising it is refused, because that number is a statement about hardware you own and the coordinator does not.

And the clamp that enforces all of it runs on the node, not on the hub. A clamp on the hub is a clamp an attacker skips by not being the hub — the moment a coordinator is compromised or merely misconfigured, it becomes remote code execution across every GPU box you have. Putting the check at the far end means the worst a bad coordinator can do is switch things off. The suite for it is written adversarially: it hands the node profiles naming interpreters, relative paths and a shell one-liner, and asserts that the running node is unchanged and every one comes back with a refusal naming the config key that stopped it.

Profiles also add no authority over your data that the hub did not have: models.remove goes down the same model-command channel as DELETE /api/admin/nodes/{id}/models/{model}, which has existed since v2.9.

Desired state, so a rebooted node fixes itself

A profile is not a command. A node asks for its profile every time it registers, so a box that was being rebuilt when you wrote one converges on the way back in — no operator action, and nothing for the hub to remember about who has what. Re-applying the same revision changes nothing and says so, which is what makes that unconditional re-ask safe rather than a re-download of forty gigabytes of weights on every reconnect.

Refusals are per item: a profile asking for one impossible thing and four possible ones applies the four and reports the one. A profile is never a startup dependency and never restarts a node — switching a tool off stops its workers in place and withdraws its capabilities from the fleet, switching it back on starts them again, and in-flight work is undisturbed. A node that rebooted because the hub said so is a node you cannot keep up.

Selectors, and what happens when two of them match

Selectors are exact: a nodeId, or a set of labels of which every pair must match. No globs, no expression language — a pattern dialect pointed at a security-relevant boundary is how a node ends up matched by a rule that reads correct. A selector that names nothing matches nothing, and is refused with a 400 rather than quietly applying to every machine you own.

If two profiles match one node, neither is sent. The node keeps what it last applied and /api/status and the console show it as conflict until you fix the selectors. Silent precedence is how a box ends up in a state that no single document explains.

Keeping them across a restart

Profiles are in memory by default and a coordinator restart forgets them. Fleet:Profiles:Persistence = file or postgres keeps them; postgres is what an HA pair wants, so both hubs read one fleet configuration. Losing them is survivable by design — every node falls back to its own configuration, which is never a wrong answer and never a capability nobody granted.

Upgrading

Nothing to do. A fleet that defines no profile behaves exactly as v3.10: the registry matches nothing, no new key appears in /api/status, and no node changes what it declares. A v3.10 node against a v3.11 hub registers and serves normally; a v3.11 node against an older hub gets no answer to its profile request, logs it at debug, and runs its own configuration.

A corpus on every node v3.12+

Turn retrieval on for a node, choose its vector engine, and let the box bring the corpus up — from one place, with no restart.

Retrieval used to be the hub's, or a standalone node's, and never both. From v3.12 it is a section in a node profile:

curl -X PUT http://localhost:5080/api/admin/profiles/edge-boxes \
  -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' -d '{
    "selector": { "labels": { "site": "sofia" } },
    "retrieval": {
      "enabled": true,
      "provider": "qdrant",
      "url": "http://qdrant.sofia.internal:6333",
      "credentialRef": "sofia-qdrant",
      "collections": ["site-sofia-docs"],
      "embeddingModel": "nomic-embed-text"
    }
  }'

The node starts the corpus while it goes on answering chat. Switch it off and the retrieval routes return to 501, the retrievals already running drain rather than fault, and the corpus is still there when you switch it back on.

One authority per collection name, and the hub knows who it is

v3.6 refused to let a meshed node hold its own corpus, because such a node holds replicas derived from its hub and an authority of its own under the same names — a collection with two truths, and a replication pass waiting to overwrite one of them. That rule is not relaxed. A node that sets LocalApi:Retrieval:Enabled by hand while it is still in a mesh fails at startup exactly as before.

What changed is that the hub can now be the one who assigns the corpus, and can therefore be the one who knows:

  • The hub records an owner per collection name: hub, or node:{id}.
  • A hub-side create of a node-owned name is a 409 naming the owner — not a mystery conflict that sends you looking for a collection which is not missing.
  • Replication and healing never target a node-owned collection. There is nothing hub-side to derive replicas from, and a placement pass over one would push an empty snapshot at its owner — the hub deleting your corpus while reporting success.

The client API does not move

Documents still go to /api/collections/{c}/documents and searches to /api/collections/{c}/search, whether the chunks are in the hub's store or on a box in another city. The hub sees a node-owned collection and dispatches the work to its owner over the connection that node already opened — so client scoping, quotas and every response shape are the ones you already had, and there is no second ingestion path to keep in step with the first.

Two refusals are said out loud rather than left to be discovered. PDF is a 415 on a node-owned collection: the PDF extractor ships with the coordinator only, and a hub that extracted the text and shipped chunks would be a second ingestion path with different chunking and a different failure mode. And an owner that is not connected is a 503 naming the node, never a quiet answer from the hub's own store — a confident answer from the wrong corpus is the failure nobody notices.

The engine, the secret and the disk stay yours

A profile names a provider and a credentialRef. It cannot carry a secret: the ref is a name, resolved on the node against LocalApi:Retrieval:Credentials:{ref}, and a name the box does not have is a refusal naming the key rather than a quiet fall back to an unauthenticated connection to your Qdrant. A hub that pushed keys down the link would be a secret distributor — credentials in profile persistence, in an admin API response, and on every node the selector matched. There is no field anywhere in a profile for a data directory either.

postgres is refused by name, with the reason: that connector needs Npgsql, which is scoped to the coordinator by design. A node runs local (its own disk) or qdrant — and Qdrant costs a node nothing, because the connector was hand-rolled over HttpClient back in v3.1 instead of taking the official gRPC client. A dependency declined two releases ago is why this one was free.

A start that fails — unreachable engine, unresolvable credential, wrong dimension — leaves the node with no corpus and a reported refusal, visible on /api/status, while the node goes on serving chat. Never a half-started corpus that answers some queries.

Upgrading

A fleet that assigns no corpus behaves exactly as v3.11 — ownership is empty, so every collection is the hub's and every code path is the one v3.11 took. One behaviour change if you script against a node: with retrieval off, /api/collections, /api/collections/{c}/documents and /api/vector/{c}/… now answer 501 with the retrieval refusal rather than 404, because a coordinator can start a corpus on a running node and the routes have to exist before it does.

OpenAI-compatible API

Almost everything in this ecosystem speaks the OpenAI wire format, and exposes exactly one knob for pointing somewhere new: a base URL.

Since v2.3.0 the coordinator serves an OpenAI-shaped surface at /v1, next to the Ollama endpoints it always had. Any OpenAI SDK, LangChain or LlamaIndex app, LiteLLM proxy, Continue/Cursor plugin, Open WebUI or n8n flow can talk to your own GPU mesh by changing one string.

EndpointNotes
POST /v1/chat/completionsBlocking and SSE streaming.
POST /v1/completionsLegacy text completion.
POST /v1/embeddingsfloat and base64 encodings — the Python SDK requests base64 by default.
GET /v1/models, GET /v1/models/{id}The models your nodes advertise.

The API key is an ordinary InferHub client key (Auth:ApiKeys) — the same one the Ollama surface uses:

from openai import OpenAI

client = OpenAI(base_url="http://your-coordinator:5080/v1", api_key="YOUR_API_KEY")

stream = client.chat.completions.create(
    model="llama3",
    messages=[{"role": "user", "content": "Explain NAT traversal in two sentences."}],
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="")

Nothing about the mesh changed to make this work: the same least-busy router picks the node, the same sticky affinity keeps a conversation on the machine that already has the model warm, and the same pre-stream failover moves the job if that machine drops before the first token. The translation happens at the coordinator's front door — the nodes have no idea a second dialect exists.

Retrieval, for free

OpenAI clients let you set default headers, so a grounded answer over your own vector collection is a two-line change to an existing app rather than a new integration:

client = OpenAI(
    base_url="http://your-coordinator:5080/v1",
    api_key="YOUR_API_KEY",
    default_headers={"X-InferHub-Retrieve": "my-collection"},
)
Where the translation is lossy — stated, not papered over.
  • n > 1 is rejected with a 400, not quietly served once.
  • Tool calls are mapped in both blocking and streaming modes (since 2.9). A streamed call arrives as one delta.tool_calls frame with index: 0 and the terminal frame resolves finish_reason: tool_calls — Ollama emits the whole call at once, so we do not fake OpenAI-style argument-fragment streaming it never produced. The full loop (streamed call → tool result → grounded answer) works with the SDK's string-form arguments.
  • logprobs, logit_bias and user are accepted and ignored.
  • Audio and video content parts are rejected, not silently dropped — a model should never answer confidently about something it was never sent. Images are forwarded since 2.11; see Vision.

Errors on /v1/* use the OpenAI envelope ({"error": {"message", "type", "param", "code"}}), because an SDK reads error.message and would otherwise surface a useless "unknown error". Since 2.11 a node's refusal is unwrapped to its innermost sentence before it lands there — Ollama encodes its own backend's JSON error as a string inside its error field, so without that a client read a wall of backslashes instead of the line saying what to fix.

Vision v2.11+

Send an image the way the OpenAI SDK already does, and it reaches whichever GPU in the fleet is holding a vision model.

Ollama serves a whole class of vision models — llava, llama3.2-vision, qwen2-vl, moondream — and the coordinator now translates OpenAI's image_url content parts into the base64 images array Ollama expects. It is a boundary translation like every other dialect mapping; the node protocol did not change.

client.chat.completions.create(
    model="llava",
    messages=[{"role": "user", "content": [
        {"type": "text", "text": "What is in this image?"},
        {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{b64}"}},
    ]}],
)

Blocking and streaming both work, and so does routing: the same least-busy router, the same sticky affinity, the same pre-stream failover. A vision request also survives the trip to an OpenAI-backed node (vLLM, LM Studio, TGI, a hosted provider) — the image is re-emitted as a data URL on the way upstream, with its media type sniffed from the magic bytes rather than guessed.

The image must be inlined as a data: URL.

A remote http(s) image URL is rejected with a 400 that says why, and that is deliberate. Fetching a caller-supplied URL would make the coordinator issue outbound requests to arbitrary hosts — an SSRF surface — and would pull third-party bytes through a hop whose whole design is to retain nothing. Every OpenAI SDK can inline a file in one line; the coordinator is not going to be a fetcher.

Two more refusals, for the same reason the rest of InferHub is loud rather than convenient. Malformed base64 fails in the translator, not seconds later from behind routing and a GPU queue. And an image format the coordinator does not recognise fails clean instead of being mislabelled — calling non-PNG bytes image/png would turn a detectable error into a bad model answer, which is far harder to notice.

Images pass through in flight, exactly like text: nothing is stored, nothing is logged, and usage stays counts-only — an image contributes to the prompt tokens the node itself reports, and we do not measure pixels. A text-only model handed an image refuses at the node, and that refusal is forwarded as-is; there is no capability registry here, because Ollama is the source of truth for what a model accepts and a second list would drift and start lying.

Authentication & configuration

InferHub keeps secrets out of source. Configure them at runtime via environment variables or .NET user-secrets — appsettings.json only ships empty placeholders.

Clients, quotas & usage (v2.7+)

A flat key list is fine until a second party is behind one of the keys. Auth:Clients gives a key an identity and, optionally, limits — every limit is nullable, and null means unlimited:

{
  "Auth": {
    "Clients": [
      {
        "Id": "acme-marketing",
        "Limits": {
          "MaxConcurrent": 4,
          "RequestsPerMinute": 60,
          "TokensPerMinute": 100000,
          "TokensPerDay": 2000000,
          "AllowedModels": ["llama3", "nomic-embed-text"]
        }
      }
    ]
  }
}

The key itself comes from env (Auth__Clients__0__Key=sk-...) or user-secrets — never a config file. A duplicate key across two clients fails startup, because attribution must never depend on list order.

What happens at the boundary, per status code:

SituationResponse
Over MaxConcurrent, RequestsPerMinute or TokensPerMinute429 with a window-accurate Retry-After
Over TokensPerDay402 Payment Required, Retry-After pointing at UTC midnight
Model outside AllowedModels404, byte-identical to a model that does not exist
Every capable node at its declared cap, longer than Queue:MaxWaitSeconds503 with Retry-After

On /v1 these use the OpenAI error envelope (rate_limit_exceeded, insufficient_quota), so SDK retry logic works out of the box.

Usage accounting. Every completed request is metered per client and per model — requests, prompt tokens, completion tokens, and whether it was served by cloud burst. Embeddings and document ingestion count too. Aggregates via GET /api/admin/usage?from&to&clientId&model, live window consumption via GET /api/admin/clients, and a Clients & usage console panel with CSV export.

What a usage record contains: a client id, a model name, a kind, two integers, a fallback flag and a timestamp. What it never contains: the prompt, the completion, a hash of either, or a "representative sample" — and there is no configuration flag to change that, because a flag is an invitation. Streaming counts come from the terminal chunk; a stream that never delivers it records nothing rather than guessing.

Counters are in-memory by default and a restart resets them. Set Usage:Persistence=postgres — with its own connection string, deliberately independent of the vector store's — to write each record to an append-only table.

Queueing. When every node holding a model is at its declared MaxConcurrency, a request waits in a bounded queue instead of failing instantly: up to Queue:MaxWaitSeconds (default 30), at most Queue:MaxDepth waiting (default 64), then 503. Nodes that declared no cap never queue. With cloud burst on no-node-or-saturated, saturation overflows to the upstream instead of queueing. Queue depth and median wait are on /api/status and the status page.

Loopback policy & production

By default, requests originating from 127.0.0.1 / ::1 skip the Bearer-token check — handy for local testing. Set Auth__RequireAuthForLoopback=true to require a token even for loopback. The same switch applies to both inference and admin routes. Remote (non-loopback) requests always require a valid token, regardless of this setting.

/health is unauthenticated so monitoring systems can poll it.

Production. Always run the coordinator behind HTTPS (a reverse proxy like Caddy / nginx, or Kestrel TLS). Bearer tokens are sensitive — don't send them over plain HTTP.

Ollama supervisor (v3.4+)

Ollama sometimes wedges — the process alive, the port open, nothing answering. The node now notices and puts it back, instead of sitting in the fleet as a passive victim of its own backend.

Since v3.36 the coordinator is told, and that is a separate switch. Restarting a process needs consent and needs to be local — Ollama:Supervisor:Enabled keeps every gate it has always had. Watching needs neither, because asking a server whether it is alive is what the next request does anyway, so Ollama:Supervisor:Watch defaults to on for any Backend:Type=ollama node, loopback or not. The node declares healthy / unreachable / wedged on its heartbeat and the hub acts on it: it stops routing there, keeps the model listed in /api/tags, and refuses the request with 503 every node holding model ‘x’ reports an unhealthy inference backend. Before this the fleet still stopped dispatching — a broken backend reports zero models, which unroutes it — but zero models and an empty box are the same thing at the hub, so what a client actually heard was 404 model not found for a model that was sitting on the disk. A vendor-typed node is never probed (that would be a billed request every fifteen seconds), and a node older than v3.36 sends nothing at all, which means no opinion and routes exactly as it always did.

Until v3.4 a wedged Ollama took the whole node out of the fleet and left it there: connected, heartbeating, reporting no models, waiting for somebody to notice. On a GPU box in a cupboard, somebody noticing can take a day. Turn the supervisor on with one key — it is off by default, because acquiring the power to kill processes on someone's machine should be opted into rather than discovered.

Two symptoms, two cures

It probes GET /api/version every ProbeInterval and acts after UnhealthyThreshold consecutive failures — one slow answer is not a fault, and a machine that reacts to a single missed probe spends its life reacting. What it does next depends on what it found.

StateHow it looksWhat it meansWhat the node does
healthyanswered inside ProbeTimeoutfinenothing
unreachablethe socket never openednot runningstart it
wedgedthe socket opened, nothing came back (or a 5xx)running but stuckstop, then start

Collapsing the last two gives you a log line that confidently reports a restart that never happened: start on a wedged process fails on a port that is already bound.

The probe has its own HttpClient, and it is not redundant with the inference one. Ollama:RequestTimeout is five minutes on purpose, because a cold 70B load takes that long; probing over it would mean a wedged Ollama takes five minutes to fail one probe and a quarter of an hour to cross a three-probe threshold.

Knowing when to stop trying

A supervisor that restarts a server every fifteen seconds forever has not fixed an outage, it has manufactured a worse one: no model ever finishes loading, so the box never comes back even when the underlying problem is gone. So restarts are budgeted — MaxRestartAttempts (3) inside RestartWindow (10 min), with a RestartBackoff that doubles between attempts, and up to ReadyTimeout (2 min) of patience for the restarted server to answer.

Past the budget the node stops restarting, says so once at error level, and keeps probing. That last part is the point: giving up on restarting is not giving up on recovering. When a human fixes the driver, or the machine finishes whatever it was choking on, the next probe succeeds and the node re-reports its models on its own — immediately, rather than waiting out ModelRefreshInterval.

Loopback only

If Ollama:Endpoint is not loopback, or Backend:Type=openai, the supervisor logs one line at startup naming why and never probes again. A shared Ollama serving four nodes, restarted because one node's network hiccuped past ProbeTimeout, is a four-node outage caused by the node with the worst link — and an OpenAI-compatible upstream (vLLM, a hosted provider) is not ours to bounce at all. A process may only be restarted by something on the same machine that can see it actually wedged. That used to cover containers by having nothing local to reach — a node image could not restart an Ollama on its host, and its endpoint was by definition not loopback. Since v3.7 the bundled image runs Ollama inside the container on 127.0.0.1, which satisfies the same rule for the right reason: an address inside the container's own network namespace cannot be anybody else's server. There, the supervisor is also the container's init system.

Where Ollama is installed as a service, the node restarts it through sc.exe / systemctl rather than running ollama serve itself — two servers fighting over :11434 is a worse outage than the one being fixed, and the one that loses is the one whose logs you are reading. A node service running under a restricted account cannot control a machine-wide one; that is reported as one line naming the privilege rather than an "Access is denied" stack trace.

Auto-install is a second opt-in

Turning the supervisor on consents to restarting a process. It does not consent to downloading and executing an installer — that is a bigger act on someone's machine, so it is its own key, off by default. It fires only when discovery finds neither a service nor a binary (i.e. "not installed", never "not answering"), once per process lifetime, with the exact command written to the log before it runs. InstallUrl points an air-gapped or policy-managed fleet at its own mirror instead of us reaching the internet from a GPU box.

One honest limitation

A restart kills whatever was streaming through that node. There is no way around it, and waiting for the work to drain first would be worse — a single stuck request would pin the node in a broken state indefinitely, which is precisely the failure this exists to end. By the time a restart happens, Ollama has not answered a trivial version check in three quarters of a minute; that stream was not going to finish. The log line says how many requests were in flight, so the cost is recorded rather than hidden.

While the backend is broken the node keeps reporting zero models. That is what stops the coordinator routing inference at it, and it is deliberate: preserving the last known good list would turn a node-local fault into client-visible timeouts. The report now says why it is empty, so "no models" no longer reads the same as "this box has nothing installed".

The full key list is in Node configuration; the Windows privilege case is covered in Windows service.

Inference backends

A node runs one backend behind the IInferenceBackend seam. The coordinator neither knows nor cares which one.

The coordinator hands a node an Ollama-shaped job and gets an Ollama-shaped response back, whatever actually ran it. Since v2.4 there was a second implementation; since v3.35 there are five values of Backend:Type, and everything that is not ollama runs through one class over one seam.

Backend:TypeDrivesWhy
ollama (default)OllamaOne machine, one model at a time, minimal ceremony.
openai (v2.4+)vLLMContinuous batching and paged attention — the difference between one GPU serving four users and one serving forty.

One implementation covers all five self-hosted servers, because they all converged on the same wire format. Three roadmap items — "vLLM backend", "llama.cpp backend", "hosted backend" — collapsed into one, entirely because v2.3's translation code could be run backwards. The three cloud dialects arrived the same way in v3.35: they were written for the coordinator's provider map in v3.30–v3.32, live in the shared library, and the node composes the same code rather than a second copy.

One consequence worth knowing: the Ollama supervisor (v3.4+) applies to ollama nodes only. On any other type it disables itself with one log line, because a vLLM, a hosted server or a cloud vendor is somebody else's to restart.

// src/InferHub.Node/appsettings.json
{
  "Backend": { "Type": "openai" },
  "Upstream": {
    "BaseUrl": "http://localhost:8000/v1",
    "TimeoutSeconds": 300,
    "Models": {
      "Include": ["meta-llama/Llama-3.1-8B-Instruct"]
    }
  }
}

Set Upstream:ApiKey through the environment (Upstream__ApiKey) or user-secrets — never in appsettings.json. A node configured with Backend:Type=openai and no BaseUrl refuses to start and names the missing key: a node that boots and then 500s on every job it is handed is worse than one that doesn't boot.

The section was called OpenAi: before v3.35, and it still binds. It is projected onto Upstream: at startup, so a node configured against any earlier release is unchanged. Writing the same key in both sections with different values fails startup naming both — which upstream receives a prompt is not decided by which section a binder applied last.
Against a cloud vendor an allowlist is not optional — it is enforced at startup. OpenRouter lists 419 model ids and Gemini around fifty, embed-only and image ones among them; a node that reported the catalogue would be telling the coordinator it can chat with an image model. So openrouter, anthropic and gemini require Upstream:Models:Include (or Node:Models:Include) and name the key if it is missing. openai is deliberately not held to this: it is usually one vLLM serving one model.

Digest and SizeBytes come back null: neither an OpenAI-compatible server nor a cloud vendor reports them, and inventing values would be worse than admitting it. /api/tags and the console render nulls as —.

A node backed by a cloud vendor (v3.35+)

Since v3.30–v3.33 a coordinator can name four vendors, give each its own credential and route to them by policy. Since v3.35 a node can be one. A machine with no GPU registers with your hub, reports the models its allowlist names, and answers jobs from Claude or Gemini — the hub cannot tell it apart from a box with a card in it. In solo mode the same process is a private, authenticated, RAG-capable OpenAI-compatible front end to that vendor, in one docker run.

// a node backed by Claude — no BaseUrl needed, and the allowlist is required
{
  "Backend": { "Type": "anthropic" },
  "Upstream": {
    "MaxTokens": 4096,
    "Models": { "Include": ["claude-sonnet-5"] }
  }
}

The credential goes in Upstream__ApiKey and is sent the way that vendor requires — Authorization: Bearer, x-api-key or x-goog-api-key. A Bearer token sent to Anthropic or Gemini is a 401 that reads like a bad key, so the header set is switched alongside the dialect rather than beside it.

One node is one upstream, and that is the design rather than a limitation. Giving the node the hub's Providers: map would be a second router on the host that has never had one — two policy vocabularies, two steer headers, and a node that can disagree with the hub that dispatched to it. The hub chooses; the node serves. A deployment that wants two vendors configures them on the coordinator, or runs two nodes.

An Anthropic-backed node declares chat and not embed, because Anthropic publishes no embeddings API. That declaration is what makes an embedding request against such a fleet a 503 naming the capability at the coordinator, before the hop — rather than a 501 buried in a failed job — and a 501 naming the reason on a solo node's /api/embed. It is the capability seam from v3.8 paying for itself a fourth time.

Two per-vendor keys are worth knowing about. Upstream:MaxTokens (default 4096) supplies the max_tokens Anthropic requires and Ollama has no equivalent for — a caller's options.num_predict always wins, and it is a ceiling rather than a target. Upstream:ThinkingBudget is Gemini's thinking budget, sent only when set: those tokens are billed as output while being reported separately from the answer's, so eval_count carries the answer alone and the invoice is larger than it. 0 switches thinking off on the models that allow it; absent leaves the vendor's own default.

Cloud burst (v2.4+)

When the router finds no node for a model, the coordinator can forward the request to a configured OpenAI-compatible upstream instead of returning 404. A GPU box that is switched off becomes degradation rather than an outage.

// src/InferHub.Coordinator/appsettings.json
{
  "Fallback": {
    "Enabled": true,
    "BaseUrl": "https://api.openai.com/v1",
    "Trigger": "no-node",                    // or "no-node-or-saturated"
    "ModelMap": { "llama3": "gpt-4o-mini" }, // the map is the consent
    "AllowedModels": []                      // empty = every mapped model
  }
}
This feature can send a user's prompt to a third party. Doing that by surprise, because somebody's desktop was asleep, is a betrayal rather than a feature. So it is fenced in, on purpose:
  • Off by default. Upgrading to v2.4 changes nothing.
  • Mapped models only. A model absent from ModelMap is never sent upstream, ever. There is no wildcard.
  • Always tagged. Every fallback response carries X-InferHub-Served-By: fallback; node-served responses carry node. Check the header, not your assumptions.
  • Always counted. /api/status and the status page report cloud burst and its counter whether it is on or off — "is this thing sending my prompts anywhere?" should not require reading a config file.
  • Never stored. The coordinator forwards in flight and streams straight through. It retains neither the prompt nor the answer — the same rule that has governed conversations since 0.7.

Trigger: no-node-or-saturated also bursts when every node holding the model is at its declared Node:MaxConcurrency. A node that declared no cap is never saturated — there is no number to compare against, and inventing one would burst to a paid upstream on a guess. And if a saturation burst fails while a node exists, the request goes to the node: bursting on saturation is an optimisation, not a promise.

With fallback disabled, a request for a model no node holds returns exactly the 404 it always has.

Named providers (v3.29+)

One upstream with no name works until you have two. Providers: is the same feature with an id on each one — its own credential, its own models, its own trigger — so an OpenAI key and an OpenRouter key can live on one hub, and llama3 can burst to one place while big-code bursts to another.

{
  "Providers": {
    "openai":     { "BaseUrl": "https://api.openai.com/v1",
                    "ModelMap": { "llama3": "gpt-4o-mini" } },
    "openrouter": { "BaseUrl": "https://openrouter.ai/api/v1",
                    "Trigger": "no-node-or-saturated",
                    "ModelMap": { "big-code": "qwen/qwen3-coder" } }
  }
}

Credentials go in the environment — Providers__openrouter__ApiKey — never in the file. Every promise in the cloud-burst warning above still holds, and two rules are new:

  • One model, one provider. Two enabled providers mapping the same model fails startup, naming the model and both providers. Taking the first is what most gateways do, and it would make the most consequential choice here — whose servers see somebody’s prompt — depend on the order your JSON keys happened to bind in. Reading a duplicate as a failover pair is worse: retrying a prompt at a second vendor is a second disclosure of it, and that needs its own argument rather than arriving by typo.
  • An unknown Type fails startup too, naming the ones that exist. Today those are openai-compatible — OpenAI, vLLM, LM Studio, TGI — openrouter since v3.30, anthropic since v3.31 and gemini since v3.32, each hand-rolled behind one interface and each its own release, so a wire-format mistake is attributable to the vendor it belongs to.

A response served by a named provider carries X-InferHub-Served-By: provider:<id>; a deployment configured through the older Fallback: block still gets fallback, because a header that quietly changes meaning is worse than one with two spellings. /api/status grows a providers array — reported whether or not anything has been dispatched, with credential reading configured or absent and never a character of the key — and /metrics grows inferhub_provider_dispatched_total{provider} beside the existing total, which still counts every request the fleet did not serve. A provider that has served nothing emits no series — and since v3.34 it does emit inferhub_provider_info, which describes what you configured rather than what happened, and shows up in the console panel with its failures and the vendor’s own words on the last one.

What v3.29 changed is who “the upstream” is, not when it is asked — a provider was still consulted only after the fleet could not serve. Since v3.33 that is a choice: Policy can make a provider the first place a model goes, per provider or per model, and a caller can steer one request either way. See Routing to a provider. A deployment that changes no config still behaves byte-identically to v3.28 — headers, status payload and metric names included.

OpenRouter (v3.30+)

Type: "openrouter" speaks the same dialect as openai-compatible — OpenRouter is OpenAI’s wire format, which is exactly why it was the first provider added after the seam, and why the same client object serves both. What the type buys is the part that was never the dialect:

"Providers": {
  "openrouter": {
    "Type": "openrouter",
    "Referer": "https://mesh.example.com",
    "Title": "Example mesh",
    "ModelMap": { "big-code": "qwen/qwen3-coder",
                  "fast": "~openai/gpt-mini-latest" }
  }
}
  • You need not type the base URL. https://openrouter.ai/api/v1 is the default. Set BaseUrl anyway if you reach it through a proxy of your own — a default that cannot be replaced is a wall.
  • The model map is checked at boot against OpenRouter’s id shape: vendor/model, optionally ~-prefixed for a floating alias and :free / :batch / :thinking-suffixed. gpt-4o-mini is a real OpenAI id and has never been an OpenRouter one; catching that at startup beats catching it as a 400 weeks later, on the one request your fleet could not serve. It is a shape check and nothing else — validating against their live /models listing would make booting depend on a vendor being up, and a listing may inform a console but may never create a route.
  • Attribution is yours to give. Referer and Title become HTTP-Referer and X-OpenRouter-Title, which list an app on OpenRouter’s public rankings. They are sent only if you set them. Filling them in with InferHub’s own name and URL would be free marketing paid for with somebody else’s deployment appearing on a vendor’s public page because they configured a model.

Token counts come back from OpenRouter’s own usage block and land in the ledger like any other. Its cost field is deliberately not read: a number InferHub did not measure does not belong in the same column as ones it did. openrouter/auto works, and the hub cannot tell you which model actually answered — it reports the name you asked for.

Two bugs fell out of reading their documentation, and both were live for every OpenAI-compatible upstream since v2.4. error.code is a number at OpenRouter and a string at OpenAI, so the whole envelope failed to parse and the upstream’s message reached you buried in the raw JSON it arrived in. And an error that happened after the response headers ended the stream quietly — a request that died at token 40 returned 200 and looked finished. Both are fixed in v3.30, for every upstream, not only this one.

Anthropic (v3.31+)

Type: "anthropic" is the first second dialect rather than a second base URL. Anthropic publishes an OpenAI-compatible endpoint and you could always point openai-compatible at it; what you got back was that layer’s idea of your usage and your errors. This speaks POST /v1/messages directly — x-api-key rather than a Bearer token, anthropic-version on every call, typed SSE events — so the token counts, the stop reasons and the error bodies are the vendor’s own. Hand-rolled over HttpClient, still zero new packages.

"Providers": {
  "claude": {
    "Type": "anthropic",
    "MaxTokens": 4096,
    "ModelMap": { "big": "claude-opus-5",
                  "cheap": "claude-haiku-4-5" }
  }
}

Providers__claude__ApiKey in the environment, as always. Four things are worth knowing before you map a model:

  • max_tokens is required by that API and Ollama has no equivalent, so MaxTokens supplies it (default 4096) and a caller’s options.num_predict always wins. It is a ceiling, not a target — the model stops at end_turn long before it, and when it does not you get done_reason: "length" rather than silence. Raise it if long answers arrive truncated: a number you cannot see is a number you cannot raise.
  • The token counts are taken, not summed. Anthropic reports usage cumulatively across the stream, and its first event already carries output_tokens: 1 before a token has been produced — so a dialect that added the frames up would report 24 tokens for a 15-token answer. Cache reads and cache writes arrive as two further numbers and are deliberately not folded into the prompt count: they are priced differently, and a total InferHub composed would match no line on your invoice.
  • seed, presence_penalty and frequency_penalty are dropped. Anthropic has no counterpart and rejects unknown parameters, so forwarding them would fail every request that carried one. Refusing here instead would break a working client over a knob the vendor never had, and approximating a seed would offer a reproducibility promise the upstream does not make. temperature, top_p, top_k, stop and num_predict all translate.
  • There are no embeddings there. An Anthropic provider serves chat; map an embedding model to a node or to another provider. The refusal names the reason rather than saying “try later” about an endpoint that will never exist.

A system message anywhere in your messages array is lifted into Anthropic’s top-level system field, in order, because that API has exactly two message roles. The mid-conversation {"role":"system"} form is real and is a 400 on some of their models, so adopting it would make the translation depend on which model you happened to map. Model ids are not shape-checked, unlike OpenRouter’s: the same model is claude-opus-5 on the first-party API, anthropic.claude-opus-5 on Bedrock and claude-…@2025… on Vertex, and BaseUrl is how you reach the latter two. Tool calls, thinking blocks and prompt caching are not translated yet.

Four wire facts were read from their documentation on the day this was written, and two contradicted the plan’s own first draft. The usage counts are cumulative; there is no [DONE] sentinel, so the stream ends at message_stop; an unknown event type must be skipped rather than fatal, because their versioning policy says new ones will be added; and an error event arriving after the response headers is raised mid-stream rather than ending the response as a 200 that looks finished. Said out loud: no live provider was called. Every payload in the test suite is a recorded one; the first real key comes out on the track’s verification day.

Gemini (v3.32+)

Type: "gemini" speaks Google’s own POST /v1beta/models/{model}:generateContent — x-goog-api-key, contents/parts, usageMetadata — rather than their OpenAI-compatibility endpoint, for the reason the section above gives: the counts, the finish reasons and the error bodies should be the vendor’s own. The third dialect behind the same interface, hand-rolled over HttpClient, still zero new packages.

"Providers": {
  "gemini": {
    "Type": "gemini",
    "ThinkingBudget": 0,
    "ModelMap": { "big": "gemini-3-pro",
                  "embed": "models/gemini-embedding-001" }
  }
}

Providers__gemini__ApiKey in the environment. Five things are worth knowing before you map a model:

  • Thinking is on by default, you pay for it, and it is not in eval_count. Gemini reports the answer’s tokens (candidatesTokenCount) and its thinking tokens (thoughtsTokenCount) as two separate numbers and bills both as output. InferHub puts the answer’s count in eval_count, because that is what a client reading the field means — so your invoice’s output figure is the larger of the two. ThinkingBudget: 0 turns thinking off on the models that allow it and makes them agree; leaving the key out keeps the model’s own dynamic default, because switching off a model’s reasoning for you would be a worse surprise than the bill.
  • Cached tokens are already inside prompt_eval_count, and are left there. Google counts cached content within promptTokenCount and reports cachedContentTokenCount as a breakdown of it — the exact opposite of Anthropic, where the cache numbers sit beside the input count. So the identical-looking arithmetic is wrong in opposite directions, and neither is adjusted: each dialect reports what its vendor calls the prompt.
  • The model id travels in the URL, and all three forms work. gemini-3-pro, the models/gemini-3-pro that GET /v1beta/models hands back, and a Vertex-style publishers/google/models/… behind a BaseUrl override. Nothing is shape-checked: a bare id gets the models/ prefix and anything containing a / is used as written, because getting it wrong the other way produces a 404 naming a model you never typed.
  • Every sampling option survives, including the three Anthropic has to drop: seed, presence_penalty and frequency_penalty all have counterparts in Gemini’s generationConfig, alongside temperature, top_p, top_k and stop. There is no MaxTokens here — that API does not require a ceiling, so none is imposed unless you send options.num_predict.
  • Embeddings are implemented, and not yet reachable from the hub. Unlike Anthropic, Gemini has an embeddings API and this dialect speaks it, over :batchEmbedContents, with no taskType sent — RETRIEVAL_DOCUMENT and RETRIEVAL_QUERY produce better vectors than the default, and nothing in an embed request says which one you meant. But /api/embed still routes to the fleet and never to a provider, so mapping an embedding model here today earns the same 404 an unknown model does. Provider-served embeddings arrive with the node-side providers in v3.35. (v3.32.0’s docs briefly said this worked; corrected in v3.32.1, after running the published image.)

A prompt the safety filters refuse comes back from Google as a 200 with no candidates and a blockReason; InferHub turns that into an error naming the reason rather than handing you an empty answer that says done: true. v3.32.1 closes the same hole on the streaming path, where the block can arrive before the stream starts and therefore not as an event: a streamed response containing no data: line at all used to have every line skipped and finish as an empty answer. It now fails, and says which of the two things arrived — a block, or the JSON array that endpoint returns when alt=sse did not reach it. That one was found by running the published image rather than by reasoning about it. Errors carry Google’s canonical status (RESOURCE_EXHAUSTED rather than just “429”) and, on a quota failure, the retryDelay they attach — the two fields a compatibility layer drops. Tools, responseSchema, thought summaries and context caching are not translated yet.

This targets :generateContent, which Google now labels legacy — and that was found by reading their documentation on the day rather than recalling it. Their newer Interactions API is generally available and recommended for new projects; generateContent “remains fully supported” with no removal date published. It is targeted deliberately: it is the surface Vertex AI and every gateway in between also speak, so a BaseUrl override reaches them; what Interactions adds — a steps[] of thoughts and tool calls, and server-side conversation state — is exactly the stateful, agentic behaviour a hub that retains nothing does not do; and its own schema changed under a dated header three months ago. If that surface is ever wanted here it will arrive as its own provider type rather than as a change to this one. Said out loud: no live provider was called. Every payload in the test suite is a recorded one; the first real key comes out on the track’s verification day.

Routing to a provider (v3.33+)

Up to v3.32 a provider was consulted only after routing failed — the router was asked first and the upstream second, so a vendor was the thing that happened when the fleet could not help. “Serve smart from Anthropic while my own boxes stay busy with local models” was not a sentence the configuration could say. Policy is that sentence, and it is the same field Trigger was, with two more values.

PolicyWhen the provider is asked
no-nodeThe default, and what every release since 2.4 did: only when no node holds the model.
no-node-or-saturatedAlso when every node holding it is at its declared MaxConcurrency.
preferFirst. The fleet is the backstop if the call fails.
onlyAlways, and a node holding that name never serves it.
 
"Providers": {
  "claude": {
    "Type": "anthropic",
    "Policy": "prefer",                       // the vendor first, the fleet as backstop
    "ModelPolicy": { "cheap": "no-node" },    // …except for this one
    "ModelMap": { "smart": "claude-opus-5", "cheap": "claude-haiku-4-5" }
  }
}
  • Trigger still binds and still means what it meant, so no existing configuration changes behaviour. Writing both and making them disagree fails startup naming both — precedence is not how this hub decides whose servers see a prompt, which is the same argument v3.29 made for refusing a model claimed by two providers.
  • ModelPolicy overrides the policy per model, because one credential often serves models you feel differently about. The alternative is declaring the same vendor twice and copying the key, and a credential written down twice is a credential rotated once. A ModelPolicy naming a model the ModelMap does not carry fails startup: a policy without a mapping is a route that does not exist.
  • The backstop is the policy’s answer, not the error’s. prefer and a saturation burst may fall back to a node when the upstream fails — falling back to your own fleet is not a second disclosure of the prompt. only and a steered request may not, and get a 502 naming the situation, because answering from different weights than the caller asked for, silently, is the one failure that looks like a success.

One request can steer itself

curl -H 'X-InferHub-Provider: claude' -d '{"model":"smart", ...}' localhost:5080/api/chat
curl -H 'X-InferHub-Provider: node'   -d '{"model":"smart", ...}' localhost:5080/api/chat

A provider id serves from that provider if it already claims the model; otherwise it is a 400 and nothing leaves the hub, because a header can never create a route your configuration does not already contain. node refuses every provider for that one request, including an only one — it is how somebody keeps a single prompt off a vendor’s servers without anybody editing config, and it costs nothing on a hub with no providers at all. A wrong steer gets one sentence, the same for an unknown id, a parked provider and a real provider that maps something else: three mistakes, one answer, so a client holding an inference key cannot enumerate your vendor configuration by probing. It is a header rather than a body field on purpose — the body is forwarded to the upstream verbatim, and a routing directive sitting inside a payload is a field a vendor will one day interpret as its own.

Neither the policy nor the steer weakens the consent model: a model that is not in a ModelMap is still never sent anywhere.

One discovery surface

/api/tags and /v1/models now list the models a named provider claims, merged with the fleet’s. Until v3.33 a mapped model no node held was a model a client could not discover and could call — the two listings said one thing and /api/chat did another. A name both hold appears once and the node’s entry wins, because digest and size are facts about a file on a box; a provider-only entry carries null for both rather than a zero somebody would later read as a measurement, and chat as its only capability, because /api/embed still routes to the fleet and never to a provider. No vendor is named: owned_by stays inferhub and X-InferHub-Served-By still answers “who served this” after the fact, so a listing never turns your configuration into a fact every client with a key can read. Models mapped by the older Fallback: block are deliberately not listed, exactly as they are absent from /api/status’s providers array — which is what keeps a hub carrying only that block identical to what it was.

One breaking change, on a three-release-old field: /api/status’s providers[] reports policy and no longer reports trigger. Two spellings of one thing on a status payload is how a dashboard ends up believing whichever key it read first. That array is null for every deployment that never wrote a Providers: block and has no console panel until v3.34, so this is the cheapest the rename will ever be. Said out loud: no live provider was called. The published image was pulled and driven the same evening — the listing, the steer’s refusals, the renamed status key and three startup refusals all check out on the artefact, and a stub vendor’s hit counter proves the refused requests never left the hub — but every one of those ran against an empty fleet, where prefer and no-node cannot be told apart by observation. Whether a real vendor honours a preferred route under load is the track’s verification day, not this release.

Running a node as a Windows service

Auto-start on boot, restart-on-failure, Event Viewer logging — one PowerShell install script.

For an always-on GPU box, run the node as a native Windows service instead of a console process. The service host (src/InferHub.Node.WindowsService) is a thin wrapper that composes the exact same node services through a shared AddInferHubNode root, so it behaves identically to dotnet run --project src/InferHub.Node — only the packaging differs. The dev/console and Linux paths are unchanged.

Publish a self-contained single-file host (no .NET runtime needed on the box):

dotnet publish src/InferHub.Node.WindowsService -c Release -r win-x64

Copy the output to C:\Program Files\InferHub\Node, set Coordinator:Url in appsettings.json, and set the enrollment secret as a machine environment variable (never commit it):

[Environment]::SetEnvironmentVariable('Coordinator__EnrollmentSecret','shared-node-secret','Machine')

Then install and start the service (run elevated):

./deploy/windows/install-service.ps1 `
  -BinaryPath "C:\Program Files\InferHub\Node\InferHub.Node.Service.exe" -DelayedStart

The install script configures automatic (or delayed-auto) start so the network and Ollama come up first, sets restart-on-failure recovery, and grants the service account write access to a writable data directory (Node:DataDirectory, default C:\ProgramData\InferHub\Node) so the node identity file survives under a least-privilege account. It logs to the Windows Event Log by default — check Event Viewer → Windows Logs → Application. The full runbook, including update/uninstall and virtual-account setup, lives in deploy/windows/README.md; a prebuilt win-x64 service + scripts are attached to the v2.1.0 release.

Linux? The equivalent is the same host pattern with builder.Services.AddSystemd() and a .service unit file — same composition root, different lifetime integration.

The Ollama supervisor and service privileges (v3.4+)

If you turn on the Ollama supervisor, this is the deployment where the service account matters. Where Ollama is itself installed as a service, restarting it means sc.exe stop Ollama / sc.exe start Ollama — and a node service running under a restricted account cannot control a machine-wide one. The failure is reported as a single line naming the privilege and the service rather than an "Access is denied" stack trace, so it is diagnosable straight from the Event Log.

Three ways out, in the order most people should try them:

  1. Run the node service as LocalSystem (the install script's default). It can control the Ollama service; nothing further is needed.
  2. Grant your virtual account rights on the Ollama service specifically — narrower than administrative rights on the box — with sc.exe sdshow Ollama to read the descriptor and sc.exe sdset to write it back with a start/stop ACE added. Paste the existing descriptor back in: sdset replaces it wholesale, and dropping the ACEs that were there is how the Ollama service becomes uncontrollable by anyone.
  3. Leave the supervisor off on this node. It is off by default, and a fleet that installs and repairs Ollama by policy does not need it.

Where Ollama is installed as a binary rather than a service, the node spawns ollama serve itself and needs only execute rights on that path — but the per-user Windows installer puts it in %LOCALAPPDATA%\Programs\Ollama, which may not be visible to the service account at all. Point Ollama:Supervisor:ExecutablePath at it explicitly, or install Ollama machine-wide.

Published on every v* tag for linux/amd64 and linux/arm64, running as a non-root app user:

In Docker there is no loopback exemption — set the keys or nothing gets through.

On bare metal InferHub skips authentication for loopback callers, which is why the from-source quickstart lets you curl localhost with no key at all. That does not carry over: inside Docker your requests are not loopback — they arrive over the bridge network from outside the container — so every call needs a real Bearer token. This is the safer default and we left it alone, but it surprises people, so the compose stack refuses to start rather than quietly come up with an empty key list you cannot authenticate against.

The OpenAI base URL becomes http://localhost:5080/v1, the console is at /console, and /health stays open for monitoring.

Where the nodes should actually run

The compose file ships a node container so up -d gives you something that works end to end — it reaches Ollama on your host via host.docker.internal (Docker Desktop) or the bridge gateway 172.17.0.1 (plain Linux). For anything real, run the node natively on the GPU box instead: it wants to sit next to a local Ollama, and passing a GPU into a container buys nothing here because the node does no compute of its own — it shells out to Ollama. On Windows that is the service host. A containerized coordinator with native nodes dialing out to it is the shape most deployments end up in.

What is exposed

All namespaced inferhub_*:

  • Fleet — requests total / in-flight / completed / failed, failovers, evictions, OpenAI-surface requests, uptime, build_info{version}.
  • Cloud burst — fallback_dispatched_total and fallback_last_model{model}, and since v3.29 provider_dispatched_total{provider} and provider_last_model{provider,model}: the same events, attributed to the vendor that served them.
  • Per node (node=) — up, cordoned, models, local in-flight, heartbeat age, routed request counters, node_tokens_per_second{node,model}, and since v3.36 node_backend_health{node,state} at a constant 1 — a node that reports no opinion (older than v3.36, watching turned off, or backed by a cloud vendor) emits nothing, because state="healthy" 0 would read as a measurement that came back bad.
  • Vector & retrieval (collection=) — replicas healed, rebuilds, under-replicated, plus per-collection queries, latency, documents, chunks and ingestion failures.
  • Queue — depth, queued / admitted / timed-out / rejected, median wait.
  • Named clients (client=) — live request and token windows against each configured limit.
  • Cluster (instance=, v3.0+) — cluster_active (1 = holds the lease) and cluster_fence (acquisition counter; a change means leadership moved). Absent entirely without Cluster:Enabled. Alert on sum(inferhub_cluster_active) != 1.
  • Capabilities (capability=, v3.13+) — capability_nodes and capability_models: how many boxes serve each capability, over how many models.
  • Tools (node=, tool=, v3.13+) — tool_requests_total{outcome}, tool_workers{state} and tool_pool{state}, as each node last reported them. Labelled by node as well as tool: a per-node counter resets when that node restarts, which Prometheus detects per series, while a fleet-wide sum would make every node bounce read as a rate spike.
  • Audio (kind=, model=, v3.13+) — audio_seconds_total and audio_characters_total. Two counters, not one: a transcription is metered in seconds and a synthesis in characters, and a single units sum would add the two into a number nobody can tell is wrong.
  • Images (kind=, model=, v3.14+) — image_megapixel_steps_total, for the same reason and as a third counter. Not an image count: width × height × steps is what a diffusion transformer actually spends, and a dashboard plotting "images" would show a flat line while somebody moved the fleet from 4-step thumbnails to 30-step 2-megapixel renders. See Text to image.
  • Image jobs (recipe=, v3.19+) — image_jobs_total{recipe,outcome} and image_job_seconds{recipe}, a real histogram with buckets at 1/5/15/60/300 s. Measured from submission, not dispatch: a job that spent four minutes queued behind somebody else's batch was four minutes slow, whatever the GPU was doing. Every outcome is counted, not just the happy one — a fleet whose failed counter was absent would look identical whether it was healthy or dropping every third render. Beside them, three fleet gauges that are always present at zero: image_queue_depth, image_jobs_active and image_retained_bytes.
  • Image recipes & cards (node=, v3.19+) — image_recipe{node,recipe,reason} is the one to alert on: reason="unlicensed" and reason="over-budget" both mean a model you configured is not being served, and nothing else in the fleet will tell you. Plus node_vram_budget_mib, _reserve_mib, _resident_mib and _measured_mib. A node with no declared budget emits no VRAM series at all — 0 would read as "this box has no VRAM", which is a different and false statement from "nobody declared a budget on this box".
  • Profiles & node corpora (v3.13+) — profile_state{profile,state} and node_corpus_records{node,collection}.Alert on state="refused" and state="conflict": both mean a box is not doing what your fleet configuration says it should.

It uses the admin key, not a client key

/metrics is operational like /health — but unlike /health it exposes node names, model names, client ids and the shape of your traffic. So it sits behind Auth:AdminApiKeys by default and is deliberately not under the bearer inference guard: a scraper is not a client, and handing a monitoring system a token that can spend GPU time would be the wrong trade.

On a trusted network, Metrics:OpenScrape=true drops the guard on this one endpoint. It never opens /api/admin/*.

The per-client series come from the in-memory admission windows — counts only. There is no prompt or completion text anywhere in the usage path, and the append-only usage ledger is never read to drive anything.

Absence is a fact, so absence is what you get

An unmeasured node/model pair has no node_tokens_per_second series rather than a zero. The router treats an unmeasured node as average, never as slow — a 0 on a dashboard would be a lie that pages someone about a node nobody has asked anything yet. Same for a client limit that is unset (unlimited is the absence of a series, not a 0 and not a -1 sentinel a graph would happily plot). The fleet counters are the opposite and are always present at zero, where a zero is a statement rather than an absence.

v3.13 holds the same line for every series it added. A capability nobody serves, a tool nobody loaded, a profile nobody wrote and a corpus nobody assigned each produce no series at all. transcription capacity: 0 on a fleet that was never asked to transcribe would page somebody at three in the morning about a feature nobody turned on.

Management console & admin API

A browser console at /console (alias for /console.html) lets an operator drive the fleet — not just watch it. It is built from the same dark-theme HTML/CSS/JS as the status page (no build toolchain, no React) and uses the same admin endpoints any script can call.

What you can do

  • Cordon / Uncordon — flip a node out of (or back into) the routing pool. A cordoned node finishes its in-flight jobs and refuses new ones; the router silently skips it when picking candidates.
  • Drain — cordon, then wait for the node's local in-flight count to reach zero. The console implements this client-side as cordon + poll, so the request stays fast and the server never holds a long-lived connection.
  • Deregister — force-disconnect a node and drop it from the registry. If the worker process is still running it will reconnect cleanly and re-register.
  • Live updates — the console subscribes to GET /api/admin/stream (Server-Sent Events) and reflects node connect / disconnect / cordon changes in ~1s without a refresh. If the stream drops it transparently falls back to polling.
  • Last-action audit — each row shows the most recent admin action (who, when), kept in memory by the coordinator.
  • v1.9 — Vector collections panel. Per-collection record count, target vs live replicas with an under-replicated badge, holder node ids, and a Rebuild button that calls the admin rebuild endpoint.
  • v1.9 — Vector activity feed. Rolling live view of the last 40 vector events (created / dropped / assigned / lost / heal.started / heal.completed) with colour cues, over the same SSE stream.

Desired beside effective, always

The most confusing state this track can produce is "I turned it on and nothing happened", and the answer is almost always a refusal. A profile asking for maxConcurrency: 8 against a box whose own config caps it at 2 is not an error and not a silent no-op: the node applies the 2, reports the refusal naming the key that stopped it, and the console shows both. The hub can only ever narrow a node, so "it did not take" needs "and here is what stopped it" beside it — or it reads as a bug.

The console shows a not-allowed row and one sentence, the manifest is on the box but Tools:Allowed does not name it. One config line instead of an afternoon.

A pool still inside its restart budget reports running, because it has not given up. A green pill there would be exactly the lie this panel exists to stop telling.

The hub now knows what a node's tools are doing

Until v3.13 the only thing a coordinator learned about a node's tools was the capability declaration folded into its model report — so a manifest present-but-not-allowed, a pool a profile had suspended, and a pool that had given up were all the same thing at the hub: nothing, and each has a different fix. Nodes now report their tool runtime up the connection they already opened, on the model-refresh loop and immediately after a profile touches it. The hub records it and never asks: a console that dialled the fleet could not show you the node that stopped answering. A node on v3.12 or earlier reports nothing, and the panel says so rather than claiming the box has no tools.

Still build-free — plain HTML, CSS and JavaScript, no bundler and no framework — and zero new dependencies.

v3.19 — it drives the image track too v3.19+

Phase 45's console answers "I turned it on and nothing happened". Underneath it, the thing that was invisible everywhere else. v3.34 — and the cloud providers v3.34+

The Cloud providers panel answers one question: where can a prompt go that is not one of my own machines? One row per provider — its type, its policy and any per-model overrides, whether a credential is set, the models it claims, how many requests it has served, how many failed, and the vendor’s own sentence about the most recent failure. This is the one panel on the console that stays visible when it is empty. A hub with no provider configured renders “No cloud provider is configured — nothing leaves your machines.” Every other panel hides when it has nothing to say; this one must not, because that sentence is the feature — a panel that disappears when the answer is the reassuring one teaches you to read absence as “I could not tell”, and that is the one state cloud burst may never be in.

A deployment still using the pre-3.29 Fallback: block gets a row too, marked legacy, and it is drawn from the fallback field of /api/status rather than from providers[]. Its credential cell is a dash for the same reason — the legacy block gains no new key for a panel, because a new field there would land in the payload of every deployment that changed nothing.

Three states also reach the Needs attention strip above the fold. A provider that is enabled, maps models and has no credential is the first, and it is deliberately not a startup refusal: an OpenAI-compatible endpoint on your own network legitimately has no key, so refusing to boot without one would break a supported deployment in order to catch a typo — which is exactly what makes it “I turned it on and nothing happened”, a 401 on the first prompt, hours later, in front of a user. The second is a provider whose last dispatch failed. Vector store

InferHub's vector store is provider-backed: VectorStore:Provider selects local (default), or, as of v2.2.0, postgres (external PostgreSQL + pgvector), or, as of v3.1.0, qdrant (external Qdrant over REST). Every endpoint, header, and client call is identical across providers — only the storage engine changes, and embeddings and inline retrieval always run on the fleet.

The local provider (since v1.5.0) is embedded on the coordinator. v1.6.0 closes the text loop. v1.7.0 spreads each collection's index across the connected nodes and lets queries be served by a node, not just the coordinator. v1.8.0 makes that placement self-healing — lose a holder and the index is rebuilt on a survivor from the raw store, automatically. v1.9.0 puts all of it on the console. v2.0.0 wires retrieval straight into /api/chat and /api/generate: the RAG mesh, GA. The local provider has two layers, kept honest:

  • Raw store — an append-only log of vector ops on disk (plus a periodic compacted snapshot) under VectorStore:DataDirectory. Plain newline-delimited JSON, one folder per collection. Source of truth, copyable, backupable. Lives on the coordinator.
  • Index — a flat (exact) cosine/dot/L2 structure in memory, rebuilt from the raw store at boot. Disposable. The coordinator always keeps a hub-local copy; from v1.7 it is also replicated to nodes.

It is off by default — flip VectorStore:Enabled to true to opt in. While disabled, the coordinator persists nothing, just like v1.4.

Replication across nodes (v1.7+)

With more than one node connected, each collection's index is replicated to a target number of them and queries can be answered by a node instead of only the coordinator. The split stays honest: the coordinator's raw store is the source of truth, and the node copies are derived from it — writes land in the raw store first, then fan out.

  • Placement. The coordinator targets VectorStore:ReplicationFactor replicas per collection (default 2, capped at the eligible node count). Cordoned nodes are skipped; placement is recomputed whenever the fleet changes (register, deregister, cordon, disconnect).
  • Push protocol over the existing SignalR link. Server → node messages (AssignVectorReplica seeds a snapshot, ApplyVectorOp forwards subsequent upserts/deletes, DropVectorReplica releases a holder). Nodes still expose nothing inbound.
  • Node-served queries. A new vector-query job kind threads through the dispatcher; reads prefer a node holding a replica (round-robin among the least-busy), falling back to the coordinator's hub-local index when none is available.
  • Hub-local index is the floor. Zero-node, one-node and many-node deployments all answer queries. The raw store on the always-on hub anchors the durability story.
  • Node-side persistence. Replicas are kept under Vector:ReplicaDirectory (default ./data/vector-replicas) using the same append-only-log + snapshot shape as the hub. The node rebuilds the index from disk at startup.
  • No full re-push on restart. The node reports its on-disk inventory (collection, lastSeq) when it registers; when the hub's lastSeq matches, the placement loop skips the re-push.

Self-healing (v1.8+)

v1.8 turns placement into a loop that keeps itself honest. A dedicated HealingService watches fleet changes (heartbeat eviction, deregister, cordon, disconnect) and the store's collection-created event; each event schedules a debounced heal pass that recomputes placement for every collection. A single in-flight gate makes the loop idempotent — a flapping fleet collapses into one settled pass rather than a storm.

  • Replica-loss detection. Subscribes to the existing lifecycle. When a holder drops, the collection falls below target and the loop re-pushes from the raw store to restore the factor.
  • Last-node-down recovery. When the live replica count for a collection hits zero, the hub-local index keeps serving reads (the floor since v1.7) and the next eligible node — a survivor, or the next to connect — is seeded from the raw store. No operator action needed.
  • New-node seeding. A node joining while the fleet is under target picks up a replica as part of the same heal loop.
  • Admin rebuild. POST /api/admin/vector/collections/{collection}/rebuild forces a heal-to-target re-push from the raw store; useful to proactively re-seed after a fleet event or to confirm replica integrity. Audit-logged as vector.rebuild.
  • Metrics. vectorReplicasHealed (each replica added by a heal), vectorRebuildsFromRaw (each last-node-down or admin rebuild), and vectorUnderReplicated (gauge of collections currently below target) join the metrics snapshot. They surface in the console in phase 17.

Console & observability (v1.9+)

v1.9 makes the mesh visible and operable. Nothing on the write path changed — this is pure surface area.

  • Status vector block. GET /api/status now returns per-collection record count, dimension, distance, target vs live replicas, holder node ids, and an underReplicated flag. Omitted when the store is disabled, so consumers that ignored the field before see no change.

PostgreSQL + pgvector (v2.2+)

Set VectorStore:Provider to postgres and point the coordinator at a PostgreSQL that has the pgvector extension. You get HNSW-indexed ANN search, real transactions, ordinary database backups, and other apps reading the same table — with every endpoint, header, and client call unchanged. Pick it when you already run Postgres, want ANN + transactions + backups you understand, or the dataset has outgrown flat-exact search. Stay local when you want zero external services, plain-file backups, and search replicas living on the GPU fleet.

The IVectorStore seam was designed for exactly this since v1.5 — the postgres provider is the second implementation behind it, proving the swap is real rather than promised.

Schema

One registry table plus one table per collection (pgvector's vector(N) column is dimension-typed, so table-per-collection is the natural mapping). An ANN index is built per the collection's distance metric, and a GIN index backs metadata filters.

CREATE TABLE inferhub.collections (
    name text PRIMARY KEY, dimension integer NOT NULL,
    distance text NOT NULL, created_at timestamptz NOT NULL DEFAULT now());

CREATE TABLE inferhub.vec_docs (
    id text PRIMARY KEY, embedding vector(768) NOT NULL,
    payload jsonb, metadata jsonb,
    seq_no bigint NOT NULL, updated_at timestamptz NOT NULL DEFAULT now());
CREATE INDEX ON inferhub.vec_docs USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);
CREATE INDEX ON inferhub.vec_docs USING gin (metadata);

Score sign-conventions match the local provider exactly, so clients see identical rankings and numbers: cosine → 1 - (embedding <=> $q) (higher is better), dot → -(embedding <#> $q) (higher is better), l2 → embedding <-> $q (lower is better). A cross-provider parity test pins identical ordering and scores within 1e-4 for all three metrics.

Honest trade-offs

Postgres is itself a durable, concurrently-queryable source of truth, so under this provider the coordinator holds no vector state on disk and does not replicate an index onto the fleet — two sources of truth would be a bug. Concretely:

  • No node replication, no self-healing, no node-served vector reads — search runs in Postgres; the replica/placement columns are zeroed and the vectorReplicasHealed / vectorRebuildsFromRaw / vectorUnderReplicated metrics stay flat.
  • The rebuild admin endpoint returns 409 (nothing to re-push), and the console disables its Rebuild button.
  • The status vector block carries a provider tag; the console shows a provider badge.
  • pgvector's ANN index tops out at 2000 dimensions — above that a collection still works but falls back to exact scan (logged at creation), never a silently broken index.
  • Moving an existing deployment here does not mean re-ingesting — since v3.3, inferhub-migrate copies a populated local or qdrant store into Postgres.

The mesh stays intact: embeddings and inline retrieval still run on the GPU nodes. Only the storage engine changed.

Qdrant (v3.1+)

Set VectorStore:Provider to qdrant and point the coordinator at a Qdrant. Pick it when you already run Qdrant or want its payload model, filtering and quantization roadmap. The connector is the third implementation behind the IVectorStore seam — and unlike the pgvector one, it added zero new dependencies: Qdrant's API is plain JSON over REST, and InferHub already speaks HTTP-to-a-server by hand (the OpenAI upstream client from v2.4), so the connector is a hand-rolled HttpClient, not the official gRPC package.

How records map

Qdrant accepts only an integer or a UUID as a point id, and InferHub ids are neither — a chunk id is a SHA-256, a document id might be a filename. So each id becomes a deterministic UUIDv5 point id and the real id, with the payload and metadata, rides in the point payload. Because the UUID is deterministic, re-ingesting a document still replaces its chunks rather than duplicating them (the idempotent-re-ingest promise from v2.5). Nothing you send or read back ever exposes the UUID. Score sign-conventions match the local provider exactly — cosine/dot higher-is-better, l2 lower-is-better — verified by a parity test that runs one dataset through all three engines and agrees within 1e-4, against a live Qdrant.

Honest trade-offs

Qdrant is itself a durable, concurrently-queryable source of truth, so — exactly as under Postgres — the coordinator holds no vector state on disk and does not replicate an index onto the fleet:

  • No node replication, no self-healing, no node-served vector reads — search runs in Qdrant; the replica/placement columns are zeroed and the heal/rebuild metrics stay flat.
  • The rebuild admin endpoint returns 409; the status vector block reports "provider":"qdrant" and the console shows a provider badge with the Rebuild button disabled.

The mesh stays intact: embeddings and inline retrieval still run on the GPU nodes. Only the storage engine changed.

Hybrid search (v3.2+)

Since v3.2, a hybrid retrieval under Qdrant is one Query API round trip that fuses a dense embedding and a sparse (lexical) vector by reciprocal rank fusion inside Qdrant — ranking by meaning and by exact terms at once, in the engine, instead of the hub stitching two searches together. The sparse vector is computed on the coordinator from the same tokenizer the local BM25 index uses (so local and qdrant agree on the lexical view of a chunk) and is IDF-weighted by Qdrant server-side via modifier: idf, so it still adds no dependency. keyword mode is now a real sparse-vector search too, not the coarse v3.1 filter.

It is opt-in per request and per collection: retrieval mode still defaults to vector, so a deployment that sends no X-InferHub-Retrieve-Mode header is byte-identical to v3.1. Collections created on v3.2+ carry the named dense + sparse vectors that hybrid needs; a collection created on v3.1 stays dense-only — it keeps answering vector queries after you upgrade, and its keyword search stays coarse until it is re-created or re-populated with inferhub-migrate (v3.3), which creates the target in the current shape.

Production Qdrant (v3.3+)

A Qdrant that is more than a demo wants three things a default collection does not have. All three are VectorStore:Qdrant: settings applied when a collection is created — existing collections are untouched, which is another reason migrating is useful.

Migrating between providers (v3.3+)

Every release since the vector store became pluggable carried the same confession: switching providers on a populated deployment meant re-ingesting from the original documents. That is awkward advice from a system that deliberately does not keep your original documents. v3.3 deletes the caveat. inferhub-migrate reads every chunk and vector out of one provider and writes them into another — local ↔ postgres ↔ qdrant, any pair, either direction.

# Dry run first: what would be copied, and where. Writes nothing.
dotnet run --project tools/InferHub.Migrate -- \
  --from local:./data/vectors --to qdrant:http://localhost:6333 --dry-run

# Then for real.
dotnet run --project tools/InferHub.Migrate -- \
  --from local:./data/vectors --to qdrant:http://localhost:6333

Each side is either a provider shorthand (local:./data/vectors, qdrant:http://localhost:6333, postgres:Host=…) or the path to a JSON config file holding a VectorStore section — a coordinator's own appsettings.json will do, which is the honest way to migrate with the exact settings the hub uses. A secret on a command line ends up in shell history, so prefer the file form when a connection string or an API key is involved.

The decisions that matter:

  • It creates each collection on the target with the same dimension and distance. A target collection that already exists with a different shape is skipped with a reason, not half-filled — the first case fails per record, and the second would succeed and silently rank differently.
  • Re-running is safe. Chunk ids are deterministic (v2.5), so a second run overwrites rather than duplicating, and an interrupted run is resumed by running it again.
  • It never deletes. A record in the target that is not in the source is left alone: a tool that removes data nobody asked it to remove is a worse failure than one that leaves a stale record behind.
  • It reports the target's own record count and exits non-zero if a collection was skipped or came up short. "The upserts returned" is not the same claim as "the data is there."
  • It is a standalone console tool and is not in the images. Moving data between stores is an operator's deliberate action, never something a running coordinator should do to itself — a hub that copied itself into another engine would be a second write path and, while the copy ran, a second truth.
  • Migrating into Qdrant creates collections in the current v3.2+ hybrid shape, so this is also how a dense-only v3.1 collection gains server-side hybrid search — without re-ingesting a single document.

One surprise worth naming. Qdrant stores the unit-normalised vector in a cosine collection (under dot and l2 it stores exactly what you sent), so a cosine collection migrated out of Qdrant carries normalised vectors — same direction, length 1. That is safe: cosine similarity is scale-invariant, so the target returns the same ids in the same order with the same scores, and there is a round-trip test that asserts precisely that. It is documented because it is surprising, and because someone diffing raw floats across a migration would otherwise reasonably conclude the copy broke. It didn't.

Document ingestion (v2.5+)

The vector store has existed since v1.5 and inline retrieval since v2.0 — but until v2.5 you had to fill the store yourself, with vectors you computed elsewhere or text pasted in by hand. Everything in between, the actual work of turning a folder of PDFs into something a model can answer from, was left as an exercise for the reader. v2.5 closes it: upload a document and the coordinator extracts its text, splits it into overlapping chunks, embeds those chunks on the GPU fleet — through the same dispatcher that serves chat, so the coordinator grows no embedding path of its own — and writes them to whichever vector store you configured.

There is no OCR, and there never will be. A PDF whose text layer is empty or near-empty is rejected with an error saying it looks like a scan. It would have been easy to bolt on an OCR pass and produce something that usually works — but a bad extraction does not fail. It succeeds, quietly, and fills your corpus with near-gibberish that retrieves plausible nonsense; the failure surfaces months later as a model that is subtly, unaccountably wrong. We would rather refuse the file. If a document genuinely needs OCR, that is a decision its owner should make deliberately, with a tool they chose, before it reaches InferHub.

Three more decisions worth knowing about, because they are the ones that would have been easy to get wrong:

  • Your file is not kept. Chunk text, a content hash and metadata — not the document. A retrieval system that also quietly becomes a document store has two sources of truth and a data-retention question its owner never agreed to answer. If you need the original, you already have it.
  • Re-ingesting is idempotent. Chunk ids derive from the document id and the chunk index, so uploading a revision replaces its chunks rather than layering a second copy underneath the first — including sweeping the tail chunks when the revision is shorter, because a stale chunk retrieves as confidently as a live one. Upload identical bytes twice and the second call does no work and says "status": "unchanged".
  • A partial ingest is a failure and says so. If the fleet goes away mid-document, the response is 500 with "status": "partial" and the chunk counts. The chunks that landed are real and visible, the document lists as partial, and re-posting the same bytes resumes rather than no-ops. A half-ingested document that claims success is worse than a failure.

Ingestion is provider-agnostic: it works identically under the file-backed local store (where the new chunks replicate to your nodes through the usual path) and under the external providers, PostgreSQL + pgvector and Qdrant. The embedding work is batched with a bounded number of chunks in flight, so ingesting a three-hundred-page manual does not starve the interactive chat traffic sharing the same GPUs. The console gained a Documents panel: pick a collection, drop a file, watch the chunk count climb, preview chunks, delete a document.

Retrieval-augmented inference (v2.0+)

v2.0 closes the RAG mesh: models can read from the store inline. Example — a grounded chat call:

curl http://your-coordinator:5080/api/chat \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "X-InferHub-Retrieve: docs" \
  -H "X-InferHub-Retrieve-K: 4" \
  -d '{"model":"llama3","messages":[{"role":"user","content":"What is InferHub?"}],"stream":false}'
  • Where the work happens. Only the search and the prompt assembly touch the hub. The embed job and the generation job are both dispatched to nodes over the existing SignalR link — no new machinery.
  • Query text. For chat, the last user message; for generate, prompt. If neither yields content, the request is passed through unchanged (or errors, per OnMissing).
  • Prompt assembly. Retrieved records are rendered as [id] text (drawn from payload.text, then payload.content, then the raw payload) and substituted into VectorStore:Retrieval:Template at the literal {context} placeholder. For chat the assembled context is inserted as a new system message after any operator-provided system messages; for generate it is prepended to prompt.
  • Failover. When retrieval can't run — unknown collection, no embedding node, empty query text, store disabled — VectorStore:Retrieval:OnMissing picks the behaviour: error returns 424 Failed Dependency; passthrough runs the original request unchanged and omits the sources header. Pre-stream failover on the generation job is unchanged.
  • Rule preserved: no conversation content on the hub. The augmented request body is assembled in-flight and forwarded to the node — nothing about the message or the retrieved context is retained on the coordinator.
  • Opt-in per request. A call without X-InferHub-Retrieve is byte-for-byte identical to v1.x — same routing, same streaming, same body.

Hybrid search & reranking (v2.6+)

Pure vector search is excellent at "what is this about" and poor at "find the exact thing I named" — ask for an error code, a part number or a surname and cosine similarity returns the general topic, not the line you wanted. v2.6 adds two answers, both per-request and both off by default.

vectorDense embedding search — the pre-v2.6 behaviour, and the default.

hybridRuns both branches and fuses them by Reciprocal Rank Fusion — by rank, not by blending scores that live on different scales. The one you usually want: it recovers the exact-match case without giving up the semantic one.
 
curl http://your-coordinator:5080/v1/chat/completions \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "X-InferHub-Retrieve: handbook" \
  -H "X-InferHub-Retrieve-Mode: hybrid" \
  -d '{"model":"llama3","messages":[{"role":"user","content":"What does error E-4021 mean?"}]}'

Reranking (X-InferHub-Rerank: true) is an opt-in pass that hands the top candidates to a chat model already on your fleet with a scoring prompt and reorders them. It costs a round trip, so it is off unless asked, and it is hard-capped by Retrieval:RerankCandidates and Retrieval:RerankTimeoutSeconds — past the timeout the un-reranked order is kept. Nothing is retained. A dedicated cross-encoder fits behind the same seam later.

Defaults are unchanged. Retrieval:Mode defaults to vector and Retrieval:Rerank to none. A deployment that sends no headers and changes no config sees results identical to v2.5 — a feature that silently changes existing results is a regression wearing a feature's clothes.

Because "hybrid improves retrieval" is an empirical claim that depends on your corpus, v2.6 ships an evaluation harness in the same release — tools/InferHub.Eval runs a golden set against a live coordinator in every mode and reports Recall@k, MRR, nDCG@k and latency. Its README carries the one warning that matters: a golden set generated by the same model you are about to evaluate is a mirror, not evidence. Run it on your own data — that is the only number that is about you. The admin console also gains a query playground that shows what each mode retrieves for a query, side by side.

Under the Qdrant provider (v3.2+), hybrid fusion runs server-side: a single Query API round trip fuses a dense and a sparse vector inside Qdrant by RRF, rather than the hub running two branches and fusing them. Same modes, same default (vector); the difference is where the fusion happens.

Multi-tenant collections (v2.13+)

Since v2.7 an API key has had an identity, a budget and a bill — but collections stayed fleet-global: any key that could ingest could, in principle, reach any corpus. Fine for a single owner; a data-isolation gap for an agency running one mesh behind several end-clients. v2.13 scopes a client key to a set of collections.

"Auth": {
  "Clients": [
    { "Id": "acme",   "Collections": ["acme-*", "shared-glossary"] },
    { "Id": "globex", "Collections": ["globex-docs"] },
    { "Id": "internal" }
  ]
}

Each entry is an exact collection name or a single trailing-* prefix — enough to hand a tenant a namespace, and small enough that nobody has to reason about a glob dialect on an isolation boundary. A client with no Collections list may touch everything, which is what every key could do before v2.13, so an existing config is unchanged.

The scope is enforced on every path that names a collection: document ingest, list, get, chunks and delete; POST /api/collections/{c}/search; the raw /api/vector/{c}/* data plane; and the X-InferHub-Retrieve inline-RAG header on both the Ollama and OpenAI surfaces.

Out of scope is a 404, not a 403 — byte-identical to a collection that does not exist, and decided before the store is ever consulted. So a name outside your scope reads the same whether or not it exists: a tenant is never told another tenant's collections are there.

Provisioning is just ingesting. A scoped client posting a document to a collection inside its scope that doesn't exist yet creates it — the dimension measured from the first embedded batch rather than guessed, the distance metric taken from VectorStore:Distance. No separate create ceremony and no admin round trip per tenant. Unscoped clients keep the old contract: collections are an admin's to create. Admin keys stay fleet-wide, and GET /api/admin/vector/collections now reports which clients can reach each collection — the view that makes a tenancy misconfiguration visible before a tenant finds it.

All of this is an authorization filter over the one vector store, not a store per tenant. One collection namespace, one source of truth, zero new dependencies.

The RAG mesh in one paragraph

Six phases, one arc. v1.5 laid the raw store; v1.6 closed the text loop by moving embeddings to the fleet; v1.7 replicated collections across nodes; v1.8 made that placement heal itself; v1.9 put it all on the console; v2.0 wires retrieval straight into inference. That's a local vector store the operator can back up as plain files, replicated across the GPU fleet, that heals itself when nodes come and go, and that the models themselves can read from — with a single header and zero external services.

Resilience & failover

InferHub is built to keep running while nodes come and go.

  • Heartbeat eviction. Nodes that miss heartbeats past NodeRegistry:TimeoutSeconds are dropped from the registry; their in-flight jobs fail with a clear error and their sticky-conversation mappings are cleared.
  • Pre-stream failover. If the chosen node drops before the first chunk is produced, the coordinator transparently retries the request on another capable node (when one exists). This applies to both blocking and streaming calls.
  • No silent retry mid-stream. Once chunks have started flowing, the coordinator does not retry — the client already has partial output. Instead the stream ends with a final error chunk so callers don't hang.
  • Job timeout. Dispatcher:TimeoutSeconds caps how long any one job can hold a request open.

High availability v3.0+

Everything above keeps the mesh running while nodes come and go. The coordinator was the remaining single point of failure — the always-on hub is the durability anchor by design, which also meant losing it lost everything. From v3.0 you can run a second one as a warm standby.

Two (or more) coordinators share one Postgres. A lease row elects exactly one active hub; the rest run standby — they answer /health, /api/status, /metrics and /api/admin/*, and return 503 with Retry-After on every inference route. When the active hub dies, the standby takes the lease within the TTL and the mesh serves again: no manual promotion, no data migration, no gossip, because the durable state was already shared.

This needs VectorStore:Provider=postgres — that is where the durable truth already lives outside any one coordinator. Under the local provider the raw store is per-hub, so those deployments stay single-coordinator. Usage persistence should be postgres too, or an invoice restarts from zero on whichever hub happens to be leading.

// Both coordinators, differing only in InstanceId.
"Cluster": {
  "Enabled": true,
  "InstanceId": "hub-a",       // "hub-b" on the other
  "ConnectionString": "",      // env Cluster__ConnectionString — the SAME database
  "LeaseTtlSeconds": 15,
  "RenewIntervalSeconds": 5
}

The node side is one key — leave it empty and the node uses Coordinator:Url exactly as before:

"Coordinator": { "Endpoints": [ "http://hub-a:8080/", "http://hub-b:8080/" ] }

A standby refuses the SignalR handshake with a 503, so walking that list is how a node finds the current leader. On demotion the old primary drops its node connections, so they go looking immediately rather than waiting out a heartbeat.

Put a load balancer or DNS failover in front — the hub does not become one. Drain on the role or on the inference 503, not on /health: a standby is healthy, it just is not leading, and an orchestrator told otherwise will restart-loop the very instance that is supposed to be waiting quietly.

Split-brain

A partitioned primary cannot be told it lost the lease — by definition it cannot reach the database that knows. So it demotes itself when it has not proved leadership within the TTL, measured on its own clock, before doing any I/O and with each attempt bounded by whatever is left of that deadline. Cluster:LeaseTtlSeconds is therefore both the worst-case failover delay and the fencing window — the same number, on purpose — and RenewIntervalSeconds must be at most a third of it, or one slow round-trip would demote a healthy leader (startup fails if it is not).

The trade is deliberate: an unreachable database takes the mesh down rather than letting two hubs both serve. A request the mesh cannot attribute to a single leader is worse than a 503 the front routes elsewhere. Watch inferhub_cluster_active on /metrics — summed across hubs it should be exactly 1; 0 means no leader, 2 would mean the fence failed.

What v3.0 does not do

Active-active load sharing (both hubs serving at once) and clustering the local vector provider are explicitly future work. This is the foundation — a survivable hub — not the whole HA track. A two-coordinator compose overlay and a failover runbook ship in deploy/docker/.

Conversations & routing

InferHub stores no conversation content. Clients send the full message history on every turn, exactly like Ollama — the coordinator only decides which node runs the work.

  • Least-busy by default. When several nodes hold the requested model, the coordinator picks the one with the lowest in-flight job count and breaks ties round-robin.
  • Measured routing (v2.8, opt-in). Set Router:Strategy=throughput and the coordinator ranks capable nodes by expected completion time — a decayed average (EWMA) of measured tokens/second per model, adjusted for in-flight load — rather than raw queue depth. A 4090 and a laptop both reporting one job in flight stop being treated as equal. A node with no measurement is treated as average, never as slow, so a fresh node still earns traffic instead of being frozen out. The default stays least-busy and is unchanged bit-for-bit; measured tokens/sec appears on /api/status and the status page.
  • Sticky conversations. Successive turns of the same chat prefer the same node, which keeps that model's KV-cache warm. Affinity expires after ~10 idle minutes — and affinity wins over the throughput strategy, because a warm model on a slower node usually beats a cold one on a faster node. (v2.12) Affinity keys on the stable node id, so a node reconnecting with a new connection keeps its warm conversations; with Affinity:Persistence=file they survive a coordinator restart too.
  • Affinity guard. If the sticky node is far busier than the least-busy alternative, the coordinator breaks affinity to avoid piling up on one machine.
  • Graceful fallback. If the sticky node disconnects, the next turn transparently routes to another capable node and the mapping is refreshed.

Tagging a conversation. By default the coordinator hashes the opening system/user message to detect a continuing thread without any client cooperation. Clients that want explicit control can attach a stable id to every turn:

curl http://your-coordinator:5080/api/chat \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "X-InferHub-Conversation: my-chat-7f3a" \
  -d '{"model":"llama3","messages":[...],"stream":false}'

The header value is opaque — any stable string identifying the conversation works.

RAG retrieval (v0.5.0). Chat and generate can now be grounded in a collection per call. Pass an InferHubCallOptions — it maps to the coordinator's X-InferHub-Retrieve[-K|-Model] headers, so the request body stays untouched — and the coordinator pulls the top matches, grounds the prompt, and echoes the record ids it used in X-InferHub-Sources. The client parses those into SourceIds on the response (works for blocking and streaming). It ships as overloads, so a call with no options behaves exactly like a plain chat. A retrieval that cannot be satisfied — store unavailable, or OnMissing=error with no hits — fails with HTTP 424 as an InferHubRetrievalException (a subclass of InferHubException), never a silent, ungrounded answer. A per-call ConversationId maps to X-InferHub-Conversation for sticky routing.

var response = await client.ChatAsync(
    new ChatRequest
    {
        Model = "llama3",
        Messages = new[] { new ChatMessage { Role = "user", Content = "How do nodes connect?" } }

    InferHubCallOptions.ForRetrieval("docs", k: 3, model: "nomic-embed-text"));

Console.WriteLine(response.Message?.Content);
Console.WriteLine(string.Join(", ", response.SourceIds ?? [])); // grounding record ids

Roadmap & status

InferHub 3.37 lets /v1/audio/speech answer while it is still speaking. A paragraph is a couple of minutes of audio and the socket was silent for all of it: the whole input was synthesised, written to a file on the node, shipped back and handed over as one body. Now OpenAI’s own stream_format takes both its values — raw bytes on a chunked body, or speech.audio.delta / speech.audio.done events — and the samples arrive as Piper makes them, one piece per sentence. Leaving the field out changes nothing, byte for byte, on a hub and on a standalone node alike. Only wav and pcm stream, because concatenability is the entire contract; the encoded formats need an encoder alive for the length of the request and a chunk boundary that is not a codec frame boundary, so asking is a 400 naming the two that work rather than a quiet fall back to a two-minute wait nothing in the response explains. The wav header is 44 bytes written once, from the first chunk, with 0xFFFFFFFF in both length fields — Piper knows its own sample rate only from its own first samples, and the measured rate goes out on a header because for pcm that is the only place it can be. The usage object the schema requires is three zeros and they are true: nothing was tokenized, and the character count that is actually billed rides on X-InferHub-Speech-Characters, because a character count in a field named tokens is a four-to-one error on somebody’s invoice. A pre-3.37 node keeps serving every buffered request and is simply not a candidate for a streaming one; a fleet with none new enough gets a 503 naming the version. And the load-bearing half is built out of v3.10.0’s own bug: SignalR’s 32 KB receive limit does not fail a message, it kills the connection, so the worker splits under that default and the node refuses to forward anything larger — ending the job with both numbers in the sentence, and retiring the worker, because an abandoned stream leaves frames on the pipe a warm worker would hand to the next caller. The test that found that asks the same mesh for something else afterwards. Still zero new dependencies and no new configuration key. Not yet established: no real voice has streamed and nobody has listened to one — that is the published-image check.

That builds on 3.36, which tells the coordinator something the node has known since 3.4: that its own inference backend has fallen over. A node whose Ollama is dead stays connected — it answers the heartbeat, the console draws it green — and the mechanism that unroutes it is that a broken backend reports zero models. That works, and at the hub it is indistinguishable from a box with nothing installed, so a request for a model whose only node had a dead server came back 404 model ‘llama3’ not found — for a fleet that has that model, sending you to pull weights already on the disk. Now the verdict travels on the heartbeat, typed: healthy, unreachable (nothing is listening — a server to start) or wedged (it accepts the socket and never answers — one to stop first), declared only after UnhealthyThreshold consecutive probes so a saturated box mid-load is not a fault. The model stays listed in /api/tags, because a client that cannot see a model cannot be told why it is unavailable; the request is refused with 503 naming the backend and a Retry-After; the console shows the state beside online rather than instead of it, and puts the node on the needs-attention strip with the fix rather than a status word. Recovery is the next heartbeat — no reconnect, no re-registration, nothing restarted on the hub. Underneath it, one query became two: who holds this model and who can serve it were the same question until a node could be up and unable to answer, so model placement no longer pulls twenty gigabytes onto a second box to replace one that will be back in a minute. And watching stopped being gated behind consent to restart: Ollama:Supervisor:Enabled keeps every gate it had — off by default, loopback only, budgeted — while the new Ollama:Supervisor:Watch defaults to on, because asking a server whether it is alive is what the next request does anyway. A vendor-typed node is never probed: a poll every fifteen seconds against a cloud vendor is a billed request. A node older than 3.36 sends nothing, and nothing means no opinion rather than sick — an upgrade that read silence as unhealthy would empty a fleet, so that case is pinned across a real connection with a real pre-3.36 payload. v3.36.1 is why you pull the image. Killing a real backend under a real node on the published artefact showed the 503 arriving on time — and reverting to the old 404 about twenty seconds later, permanently. The empty model report a broken node sends (the pre-3.36 unrouting mechanism) was still landing, taking the model out of the registry, so there was no longer a model for the hub to refuse by name. Two patches came out of that. 3.36.1 taught the hub to hold an empty inventory from a node that has declared an unhealthy backend — and re-running the check showed that half-fixes it, because on default settings the empty report normally arrives before the probe threshold is crossed, while the hub still believes the node is healthy. 3.36.2 fixes the root: the node was catching a failed model listing and returning an empty list, reporting a failure to the coordinator as data — and no hub can tell that from a box whose weights were deleted. ListModelsAsync now answers null for “could not be asked” and the node sends nothing at all, leaving the inventory alone while the heartbeat carries the verdict. That is a rule this codebase already had, from v2.5: “not fetched” must not be confusable with “not there”. Every test passed before both fixes and had to: they drive the registry directly and never send the report a live node sends on a timer. Still zero new dependencies. See the supervisor.

InferHub 3.35 gives a node the four dialects the coordinator has had since 3.32. Until now Backend:Type was ollama or openai, so two of the four clients — Anthropic’s /v1/messages and Gemini’s :generateContent, both already written, both already in the shared library — were unreachable from the box that has the GPU, and a machine somebody wanted to run as a node backed by Claude could not be configured at all. It now can: a node on a cloud vendor registers with your hub, reports the models its allowlist names and answers jobs the hub cannot tell apart from a local one — or, in solo mode, is a private, authenticated, RAG-capable front end to that vendor in one docker run. It is the same code composed twice, not a second implementation, which is what made a release out of what would otherwise have been three. One node stays one upstream, deliberately: giving the node the hub’s provider map would be a second router on the host that has never had one, and a node that can disagree with the hub that dispatched to it — the hub chooses, the node serves. Two things follow from doing it properly. The config section is now Upstream: rather than OpenAi:, because a key called OpenAi:AnthropicVersion is the kind of key somebody screenshots — the old section still binds, and writing the same key in both with different values fails startup naming both. And a backend now declares which capabilities it serves, so an Anthropic-backed node says chat and not embed: an embedding request against such a fleet is a 503 naming the capability at the coordinator, before the hop, instead of a 501 buried in a failed job. That builds on 3.0, which removed the last single point of failure. The always-on coordinator was the mesh's durability anchor by design — which also meant losing it lost everything. Now a second coordinator can run as a warm standby over the same Postgres: one holds a lease and serves, the other waits. Kill the active hub and the standby takes the lease, the nodes reconnect to it on their own, and the mesh keeps serving — no manual promotion and no data migration, because the durable state was already shared. A coordinator that cannot prove it still holds the lease demotes itself within the TTL on its own clock, so a partition stops a hub serving rather than letting two of them both answer. Honestly scoped: this is the foundation of the HA track — active-active load sharing and clustering the local vector provider are still to come. Off by default, so single-coordinator setups are byte-identical to 2.13, and still zero new dependencies — the lease is one Postgres row. See High availability.

That builds on 2.13, which makes the mesh multi-tenant where it counts: RAG collections can now be scoped to a client key. One mesh, several end-clients, and tenant A simply cannot see, ingest into, search or retrieve from tenant B's corpus — on any path, including the inline-RAG header on both surfaces. A collection outside your scope returns a 404 rather than a 403, decided before the store is consulted, so nobody even learns it exists. Provisioning is just ingesting: post into a new collection inside your scope and it is created, with the dimension measured from the embeddings rather than guessed. Admin keys stay fleet-wide. It is an authorization filter over the single vector store — still one source of truth — and a config that never heard of scoping runs exactly as it did in 2.12. See Multi-tenant collections.

That builds on 2.12, which makes sticky routing survive a bounce. Conversation affinity now keys on the stable node identity rather than the SignalR connection, so a node reconnecting keeps its warm conversations; with opt-in Affinity:Persistence=file a coordinator restart keeps them pinned too, so a chat that was mid-flight doesn't pay for a cold model reload. The persisted map is a derived cache of routing hints — a lost entry costs one cold load, never a wrong answer — and it is off by default. See Conversations & routing.

That builds on 2.11, which sees images. The OpenAI-compatible surface used to reject image content parts outright, which locked out the whole vision-model class Ollama already serves — llava, llama3.2-vision, qwen2-vl, moondream. Send a base64 image the way the OpenAI SDK does and it now reaches whichever GPU in the fleet can read it, blocking or streaming, and through an OpenAI-backed node too. It will not fetch a remote http image URL — that would make the coordinator issue outbound requests to caller-supplied hosts — and it will not guess a media type it cannot recognise, because mislabelling bytes turns a detectable error into a bad model answer. Nothing about the image is stored or logged, usage stays counts-only, and text-only requests are byte-identical to 2.10. Still zero new dependencies. See Vision.

That builds on 2.10, which gives the mesh a scrape endpoint. Everything it measured was in-memory and readable only as a status snapshot; now GET /metrics serves the Prometheus text exposition format — fleet in-flight, measured tokens/second per node and model, queue depth and outcomes, retrieval latency per collection, per-client token windows — so those numbers get a history, a graph and an alert. A Prometheus + Grafana overlay with a starter dashboard ships in deploy/docker/. It measures nothing new and /api/status is unchanged; the endpoint is admin-key-guarded by default, because unlike /health it exposes node names and traffic shape. The exposition format is written by hand, so it is still zero new dependencies. See Prometheus /metrics.

That builds on 2.9, which finishes tool calling on the OpenAI-compatible surface. Function calls were mapped in blocking mode only; now they stream too, as proper delta.tool_calls frames — so a streaming agent loop (the OpenAI SDK, LangChain, LlamaIndex) gets the call the moment it lands rather than a bare finish_reason with nothing attached. The whole call arrives in one delta and the terminal frame resolves finish_reason: tool_calls; we do not fabricate OpenAI-style argument-fragment streaming that Ollama never sent. Text-only streaming is byte-identical to before, the node protocol is unchanged, and the full call → tool-result → answer loop was verified live against a real GPU node. See OpenAI-compatible API.

That builds on 2.8, which makes a mixed fleet pleasant to run. The coordinator can finally act on the fleet's models — pull, delete and warm from the console or admin API, with a progress bar, over the connection each node already holds open (no inbound port), plus an ensure?replicas=N placement call and a fleet-wide model matrix. And the router stops pretending a 4090 and a laptop are the same node: opt-in Router:Strategy=throughput ranks nodes by measured tokens/second — an EWMA computed from data every job already reported — while an unmeasured node is treated as average, never starved, and sticky affinity still wins. The default routing is unchanged, bit for bit. See Fleet operations.

That builds on 2.7, which gives an API key a name, a budget, and a bill. Auth:Clients turns a flat list of anonymous keys into named clients with per-key concurrency, rate and token limits and a model allowlist; every completed request is metered per client and per model — counts, never text — queryable from the admin API, visible on the console, exportable as CSV, and optionally persisted to Postgres. Over a limit is a 429 with Retry-After; over the daily budget a 402; a fleet at capacity queues briefly, with a real bound, then says 503. Existing configs run unchanged. See Clients, quotas & usage.

That builds on 2.6, which goes after retrieval quality. Pure vector search is excellent at "what is this about" and poor at "find the exact thing I named", so retrieval now has three per-request modes — vector, keyword (BM25), and hybrid, which runs both and fuses them by rank (RRF) — plus an opt-in reranker that reuses a model already on your fleet. And because "hybrid improves retrieval" is a claim rather than a feeling, the same release ships an evaluation harness that measures it on your corpus. Defaults are unchanged: send no headers and results are identical to 2.5.

That builds on 2.5, which lets you fill the vector store at last. Upload a document — text, Markdown, HTML, JSON, or a PDF's text layer — and the coordinator extracts it, chunks it, embeds the chunks on your GPU fleet through the same dispatcher that serves chat, and stores them; any request carrying X-InferHub-Retrieve then comes back grounded, with citations down to the document and page. Three things it deliberately does not do: keep your file (chunks and a hash, nothing else), duplicate silently (re-ingesting replaces; identical bytes are a no-op and say so), or OCR (a scanned PDF is rejected with an error, not turned into a corpus of confident gibberish).

That builds on 2.4, which taught the mesh to speak the OpenAI format upstream, not just to its clients. A node is no longer synonymous with Ollama: set Backend:Type=openai and it drives vLLM — continuous batching, the difference between one GPU serving four users and one serving forty — or llama.cpp's server, LM Studio, TGI, or a hosted provider. One backend implementation covers all of them, because they all landed on the same dialect. The same release adds cloud burst: when the fleet holds no node for a model, the coordinator can fall back to a configured upstream instead of returning a flat 404 — off by default, mapped models only, tagged in every response, counted on the status page, and never stored.

That builds on 2.3, which made the mesh reachable from the tools you already use: an OpenAI-compatible API at /v1 alongside the Ollama endpoints, so any OpenAI SDK, LangChain app or IDE plugin can point at your own GPU pool by changing one base URL — with the same router, sticky affinity, failover and inline retrieval running underneath. It also brought published container images and a compose stack, so a coordinator is one command away instead of two terminals.

That builds on 2.0, which closed the RAG mesh: add X-InferHub-Retrieve: <collection> to a normal /api/chat or /api/generate call and the coordinator embeds the query on a GPU node, searches the store (node replica if available, hub-local otherwise), assembles a grounded prompt, and dispatches the generation to a node. Retrieval is opt-in per request — without the header, calls are byte-for-byte identical to v1.x. Underneath sit v1.9's console surface, v1.8's self-healing replicas, v1.7's replication push-protocol, v1.6's text-in/vectors-out loop, the v1.5 vector store, and the v1.4 base (Bearer auth, sticky + least-busy routing, live streaming, pre-stream failover, typed/validated node config, an admin API, and a live management console). On the deployment side, 2.1 runs a node as a native Windows service without changing the cross-platform worker, and 2.2 makes the vector store pluggable with PostgreSQL + pgvector as the first alternative backend.

Reading their documentation on the day rather than recalling it turned up four facts that shape the code, two of which contradicted the plan’s own first draft — the streamed token counts are cumulative, so they are taken rather than summed. v3.32 is the third: Gemini’s own :generateContent, on the same terms — and reading their docs on the day found the native surface is now the vendor’s legacy one, which is written down rather than worked around, because what their newer Interactions API adds is precisely the stateful, agentic behaviour this hub does not do.
